EXAM QUESTION 1 : SCENARIO REQUIREMENT CLASSIFICATION

Question 1: Requirements Identification and Categorization (Functional, Non-Functional, Domain & Constraints)
[ภาษาไทย]: การระบุและจำแนกประเภทความต้องการ (ความต้องการเชิงหน้าที่, เชิงคุณลักษณะ, เชิงโดเมน และข้อจำกัดโครงการ)

หัวข้อ: Chapter 4 & Practice-ReqEng (PizzaFriend / FreshMart Model) • คะแนนโดยประมาณ: 20 - 25 คะแนน
[English Problem Scenario]: "SmartCampus" University Express Delivery & Locker System
KMUTNB University plans to launch a campus-wide smart parcel delivery system called "SmartCampus" to solve the issue of misplaced packages and long waiting lines at the mailroom. Students and staff must register and log in using their university email. When a parcel arrives at the campus mail hub, staff can scan the tracking barcode and assign it to an automated smart locker. The system must immediately send an SMS and email notification to the recipient containing a secure 6-digit pickup OTP code and a QR code. Recipients can open their assigned locker by scanning the QR code or typing their OTP at the locker kiosk. The system must calculate storage fees if a package is left in a locker for more than 48 hours and accept payments via Mobile Banking QR Code before releasing the door. The kiosk UI must be intuitive, allowing users to collect their parcel within 30 seconds. The system must handle at least 800 concurrent users during peak rush hours (12:00-13:30) with a response time under 2 seconds. All student personal data and contact records must comply strictly with Thailand's Personal Data Protection Act (PDPA). The mobile client must be built using Flutter to support both iOS and Android, and the server must integrate with the university's Active Directory student database. The entire project must be completed within 3 months with a budget not exceeding 250,000 Baht.
[คำแปลโจทย์ภาษาไทย]: มหาวิทยาลัยต้องการพัฒนาระบบรับส่งพัสดุและตู้ล็อกเกอร์อัจฉริยะ "SmartCampus" นักศึกษา/บุคลากรต้องล็อกอินด้วยอีเมลสถาบัน เมื่อพัสดุมาถึงเจ้าหน้าที่จะสแกนบาร์โค้ดเพื่อนำเข้าตู้ ระบบต้องส่ง SMS และ Email พร้อมรหัส OTP 6 หลัก และ QR Code ให้ผู้รับทันที ผู้รับสามารถสแกน QR หรือกด OTP ที่หน้าตู้เพื่อเปิดรับของได้ หากฝากเกิน 48 ชม. ระบบต้องคำนวณค่าปรับและรองรับการจ่ายเงินผ่าน Mobile Banking QR Code ก่อนเปิดตู้ หน้าจอใช้งานง่ายรับของได้ใน 30 วินาที รองรับผู้ใช้พร้อมกัน 800 คน ตอบสนองใน 2 วินาที ข้อมูลต้องปลอดภัยตาม PDPA พัฒนาด้วย Flutter รองรับ iOS/Android ต่อระบบ Active Directory มหาลัย และเสร็จใน 3 เดือน งบไม่เกิน 250,000 บาท
1. Functional Requirements (ความต้องการเชิงหน้าที่ — What the system shall do)
• The system shall allow students and staff to register and log in using their university email.
ระบบต้องอนุญาตให้นักศึกษาและบุคลากรลงทะเบียนและเข้าสู่ระบบด้วยอีเมลของมหาวิทยาลัยได้
• The system shall allow mailroom staff to scan parcel barcodes and assign them to specific smart lockers.
ระบบต้องให้เจ้าหน้าที่สแกนบาร์โค้ดพัสดุและระบุตู้ล็อกเกอร์อัจฉริยะสำหรับจัดเก็บพัสดุได้
• The system shall automatically send an SMS and email notification with a 6-digit OTP and QR code to the recipient upon parcel deposition.
ระบบต้องส่งการแจ้งเตือนทาง SMS และอีเมลพร้อมรหัส OTP 6 หลัก และ QR Code ไปยังผู้รับทันทีเมื่อพัสดุเข้าตู้
• The system shall verify the QR code or OTP at the locker kiosk to unlock the assigned locker door.
ระบบต้องตรวจสอบความถูกต้องของ QR Code หรือรหัส OTP ที่ตู้คีออสเพื่อปลดล็อกเปิดประตูตู้
• The system shall calculate overtime storage fees if a package is stored for over 48 hours.
ระบบต้องคำนวณค่าธรรมเนียมการฝากเกินเวลาโดยอัตโนมัติหากฝากพัสดุไว้นานเกิน 48 ชั่วโมง
• The system shall accept payments via Mobile Banking (PromptPay QR Code) before releasing the locker door.
ระบบต้องรองรับการชำระเงินผ่าน Mobile Banking (สแกน PromptPay QR Code) ก่อนปลดล็อกตู้ในกรณีมีค่าปรับ
2. Non-Functional Requirements (ความต้องการเชิงคุณลักษณะ — How the system should perform)
• Usability: The kiosk interface must be intuitive, allowing users to complete parcel pickup within 30 seconds without prior training.
ด้านการใช้งาน (Usability): หน้าจอใช้งานง่าย สามารถทำรายการรับพัสดุเสร็จสิ้นได้ภายใน 30 วินาทีโดยไม่ต้องฝึกอบรม
• Performance: The system shall respond to user inputs and QR scans within 2 seconds.
ด้านประสิทธิภาพ (Performance): ระบบต้องตอบสนองต่อการสั่งการและการสแกน QR Code ภายในเวลาไม่เกิน 2 วินาที
• Capacity / Scalability: The system must support at least 800 concurrent users during peak hours without performance degradation.
ด้านการรองรับผู้ใช้ (Capacity): ระบบต้องรองรับผู้ใช้งานพร้อมกันอย่างน้อย 800 คนในช่วงเวลาเร่งด่วนโดยระบบไม่ช้าหรือล่ม
• Security: Customer personal data and OTP credentials must be encrypted during transmission and storage.
ด้านความปลอดภัย (Security): ข้อมูลส่วนบุคคลและรหัส OTP ต้องได้รับการเข้ารหัสอย่างปลอดภัยขณะส่งผ่านเครือข่ายและจัดเก็บ
3. Domain Requirements (ความต้องการเฉพาะด้านโดเมน)
• The system must integrate with the university's Active Directory authentication service for student/staff credential verification.
ระบบต้องเชื่อมต่อกับระบบฐานข้อมูล Active Directory ของมหาวิทยาลัยเพื่อยืนยันสถานะนักศึกษาและบุคลากร
• The system must strictly comply with Thailand's Personal Data Protection Act (PDPA) regarding parcel recipient data handling and retention.
ระบบต้องปฏิบัติตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA) ของประเทศไทย ในการเก็บรักษาและทำลายข้อมูลผู้รับพัสดุ
4. Constraints (ข้อจำกัดของโครงการ)
• The mobile application must be developed using the Flutter framework to support both iOS and Android from a single codebase.
ทีมพัฒนาต้องใช้ Flutter Framework เพื่อให้แอปพลิเคชันรองรับทั้ง iOS และ Android ด้วย Source Code ชุดเดียวกัน
• Total project development cost must not exceed 250,000 Baht.
งบประมาณในการพัฒนาทั้งหมดต้องไม่เกิน 250,000 บาท
• The system must be fully developed, tested, and deployed ready for launch within 3 months.
ระบบต้องพัฒนา ทดสอบ และเปิดให้บริการจริงได้ภายในระยะเวลาไม่เกิน 3 เดือน
⭐ เทคนิคการทำข้อสอบ: เขียนแยกเป็น 4 หัวข้อชัดเจนตามนี้ ใช้คำว่า "ระบบต้อง..." หรือ "The system shall..." และระบุตัวเลขที่วัดผลได้ (Testable metric) ใน NFR

(b) A software company is awarded three projects:
  1. Project A: An Embedded Insulin Pump Controller (Safety-critical medical system).

แนวคิดหลัก (Core Concept) ทำงานเป็นขั้นตอนตามลำดับ (Sequential / Plan-driven) แต่ละเฟสต้องเสร็จสมบูรณ์ก่อนเริ่มเฟสถัดไป แบ่งระบบเป็นส่วนย่อย (Increments) ทยอยพัฒนา ส่งมอบ และประเมินผลทีละเวอร์ชันร่วมกับผู้ใช้ นำซอฟต์แวร์หรือคอมโพเนนต์สำเร็จรูปที่มีอยู่แล้ว (COTS / Web Services) มาปรับแต่งและประกอบเข้าด้วยกัน
ข้อดี (Advantages) • โครงสร้างชัดเจน จัดการง่าย
• วางแผนระยะเวลาและงบประมาณได้ชัดเจนตั้งแต่เริ่มโครงการ
• มีเอกสารประกอบครบถ้วนทุกขั้นตอน 		• รองรับการเปลี่ยนแปลง Requirement ได้ดีมาก
• ลดต้นทุนในการแก้ไขงาน (Rework cost)
• ลูกค้าได้ใช้ฟังก์ชันสำคัญก่อนและให้ Feedback ได้เร็ว 		• ลดต้นทุนและความเสี่ยงอย่างมาก
• ส่งมอบระบบได้รวดเร็วทันที (Fast time-to-market)
• ใช้โค้ดที่ผ่านการทดสอบมาแล้ว
ข้อเสีย / ความเสี่ยง (Disadvantages) • ปรับเปลี่ยน Requirement ภายหลังได้ยากและแพงมาก
• ลูกค้าเห็นผลงานจริงตอนจบโครงการเท่านั้น (Late customer value)
• ไม่เหมาะกับระบบที่ความต้องการเปลี่ยนแปลงบ่อย 		• ผู้บริหารติดตามความคืบหน้ายาก (Process is not visible / เอกสารไม่ครบทุกรอบ)
• โครงสร้างระบบ (Architecture) อาจเสื่อมลงหากไม่ Refactoring สม่ำเสมอ 		• ต้องยอมประนีประนอม Requirement ตามฟังก์ชันของ COTS
• ขาดอำนาจควบคุมการอัปเดตและคุณภาพของ Third-party (Loss of control)
ความเหมาะสม (Project Suitability) ระบบขนาดใหญ่ที่มีความต้องการนิ่งและชัดเจนมาก, ระบบ Safety-critical, โครงการที่แบ่งพัฒนาหลายทีม/หลายไซต์ ระบบธุรกิจทั่วไป, เว็บ/แอปพลิเคชันที่ต้องการเปิดตัวไวและปรับปรุงตามความต้องการของผู้ใช้อย่างต่อเนื่อง ระบบมาตรฐานทั่วไปในตลาดที่มีโซลูชันสำเร็จรูปพร้อมใช้อยู่แล้ว เช่น ระบบ ERP, CRM, E-commerce พื้นฐาน
(b) การเลือก Process Model ให้เหมาะสมกับโจทย์แต่ละข้อและเหตุผลประกอบ
• Project A (Insulin Pump Controller): Selection -> Waterfall Model (Plan-driven)
Justification: The insulin pump is a safety-critical embedded system where software bugs can cause severe injury or death. It requires complete, formal, and upfront specification, rigorous verification, and exhaustive safety analysis before implementation begins. Requirement changes are minimal.
เหตุผลภาษาไทย: เป็นระบบความปลอดภัยวิกฤต (Safety-critical system) ข้อผิดพลาดอาจทำให้คนไข้เสียชีวิตได้ จึงต้องมี Specification ที่สมบูรณ์แบบตั้งแต่ต้น มีการทดสอบความปลอดภัยอย่างเข้มงวด และ Requirement มีความคงที่ ไม่ควรปรับเปลี่ยนระหว่างทาง จึงเหมาะกับ Waterfall Model
• Project B (E-commerce Food Delivery Startup App): Selection -> Incremental Development Model (Agile)
Justification: The market demands rapid delivery and continuous customer feedback. It is impractical to specify all requirements upfront. Developing in small increments allows early delivery of core ordering features and rapid accommodation of evolving business needs.
เหตุผลภาษาไทย: ธุรกิจ Startup ต้องการความรวดเร็วในการนำสินค้าเข้าสู่ตลาด (Time-to-market) และไม่สามารถระบุความต้องการได้ครบตั้งแต่แรก การทำแบบ Incremental ช่วยให้ปล่อยฟีเจอร์สั่งอาหารหลักออกมาก่อน แล้วนำ Feedback จากผู้ใช้มาปรับปรุงในเวอร์ชันถัดไปได้ทันที
• Project C (Enterprise Inventory Management using SAP/COTS): Selection -> Reuse-oriented Software Engineering
Justification: Enterprise inventory management has standard business logic available in mature off-the-shelf COTS packages. Using reuse-oriented development saves substantial time and cost by configuring existing components rather than developing from scratch.
เหตุผลภาษาไทย: ระบบจัดการสินค้าคงคลังองค์กรเป็นกระบวนการมาตรฐานที่มีซอฟต์แวร์สำเร็จรูป (COTS เช่น SAP) รองรับอยู่แล้ว การใช้ Reuse-oriented ช่วยประหยัดเวลาและงบประมาณอย่างมาก เพียงแค่นำมา Config ให้เข้ากับธุรกิจโดยไม่ต้องเขียนใหม่ทั้งหมด
⭐ เกณฑ์การให้คะแนน: ให้คะแนนคู่กันทั้ง "การเลือกรุ่นจำลองที่ถูกต้อง" และ "เหตุผลสนับสนุนที่สอดคล้องกับลักษณะของระบบ" (System Nature & Criticality)

[คำแปลโจทย์ภาษาไทย]:
(a) จงนิยามและอธิบาย 4 คุณลักษณะสำคัญของซอฟต์แวร์ที่ดี (4 Essential Attributes of Good Software) ตามหลักการของ Ian Sommerville

(a) 4 คุณลักษณะสำคัญของซอฟต์แวร์ที่ดี (4 Essential Attributes of Good Software)
คุณลักษณะ (Attribute) คำอธิบายภาษาอังกฤษ (Sommerville Definition) คำอธิบายภาษาไทยและตัวอย่าง
1. Maintainability
(ความสามารถในการบำรุงรักษา)		 Software should be written in such a way that it can evolve to meet the changing needs of customers. ซอฟต์แวร์ต้องเขียนและออกแบบให้ง่ายต่อการแก้ไข ปรับปรุง และเพิ่มเติมฟังก์ชันตามการเปลี่ยนแปลงของธุรกิจในอนาคต โค้ดต้องอ่านง่าย มีโครงสร้างที่ดี
2. Dependability & Security
(ความเชื่อถือได้และความปลอดภัย) 		Includes reliability, security, and safety. Software should not cause physical or economic damage in system failure. ระบบต้องทำงานถูกต้อง น่าเชื่อถือ ปลอดภัยจากการโจมตี และไม่ก่อให้เกิดความเสียหายต่อชีวิต ทรัพย์สิน หรือเศรษฐกิจเมื่อระบบขัดข้อง
3. Efficiency
(ประสิทธิภาพในการใช้ทรัพยากร)		 Software should not make wasteful use of system resources such as memory and processor cycles (responsiveness, processing time). ซอฟต์แวร์ต้องไม่สิ้นเปลืองทรัพยากรระบบ เช่น CPU, RAM, Network Bandwidth และต้องมีเวลาตอบสนองที่รวดเร็ว (Response time)
4. Acceptability
(การยอมรับจากผู้ใช้งาน)		 Software must be acceptable to the users: understandable, usable, and compatible with other systems they use. ซอฟต์แวร์ต้องได้รับการยอมรับจากผู้ใช้จริง ใช้งานง่าย (Usable) ไม่ซับซ้อน เข้ากันได้กับอุปกรณ์และระบบเดิมที่มีอยู่
(b) โครงสร้างต้นทุนของวิศวกรรมซอฟต์แวร์ (Software Engineering Costs)
• Development vs Testing: Roughly 60% of software costs are development costs, and 40% are testing costs.
• ต้นทุนการพัฒนาซอฟต์แวร์แบ่งเป็น: ค่าใช้จ่ายในการพัฒนาประมาณ 60% และค่าใช้จ่ายในการทดสอบระบบ (Testing) ประมาณ 40%
• Custom Software Evolution: For custom software, evolution (maintenance) costs often exceed development costs by several times throughout the software lifespan.
• ซอฟต์แวร์ที่สร้างเฉพาะงาน (Custom Software): ต้นทุนการปรับปรุงบำรุงรักษา (Evolution/Maintenance) มักจะสูงกว่าต้นทุนการพัฒนาแรกเริ่มหลายเท่าตัว
(c) การวิเคราะห์กรณีศึกษาจริยธรรมตามหลัก ACM/IEEE Code of Ethics
แนวทางการตัดสินใจและการตอบข้อสอบ:
วิศวกรซอฟต์แวร์ "ต้องปฏิเสธคำสั่งปล่อยระบบและไม่ยินยอมให้ข้ามการทดสอบความปลอดภัย" โดยเด็ดขาด เนื่องจากเป็นระบบการแพทย์ที่มีผลต่อชีวิตมนุษย์
1. Principle 1: PUBLIC (Public Interest): Software engineers shall act consistently with the public interest. The health, safety, and welfare of patients override any business deadline or profit.
ด้านความรับผิดชอบต่อสาธารณะ (Public): ต้องคำนึงถึงความปลอดภัยและชีวิตของประชาชนเป็นอันดับแรก การปล่อยซอฟต์แวร์ที่ไม่ผ่านการทดสอบอาจส่งผลให้ผู้ป่วยเสียชีวิต
2. Principle 3: PRODUCT (Product Quality): Engineers shall ensure high professional standards. Knowingly releasing defective or untested safety-critical software directly violates professional duty.
ด้านคุณภาพของผลิตภัณฑ์ (Product): วิศวกรต้องส่งมอบงานที่มีมาตรฐานการทดสอบที่สมบูรณ์ ไม่ปล่อยผ่านระบบที่มีความเสี่ยงร้ายแรง
3. Principle 4: JUDGMENT (Integrity): Engineers must maintain integrity and professional independence. You must not allow managerial pressure to override ethical judgment.
ด้านดุลยพินิจและความซื่อสัตย์ (Judgment): ต้องรักษาความเป็นอิสระทางวิชาชีพ ไม่ยอมโอนอ่อนต่อแรงกดดันจากผู้จัดการเมื่อขัดต่อหลักความปลอดภัย
⭐ เทคนิคการตอบ: อ้างอิงคำว่า "Public Interest must be primary" และระบุหลักการ ACM/IEEE 4 ด้านหลัก (Public, Product, Judgment, Client/Employer)

ระดับน้ำตาลเพิ่มขึ้น และอัตราการเพิ่มสูงขึ้นหรือคงที่ (r2 - r1) ≥ (r1 - r0) CompDose = round((r2 - r1)/4)
(หากค่าปัดเศษ = 0 ให้จ่าย MinimumDose)
(c) 5 เกณฑ์การตรวจสอบความถูกต้องของ Requirements (Requirements Checking Criteria)
1. Validity (ความสมเหตุสมผล): Does the system provide the exact functions that best support the customer's actual operational needs?
ระบบมีฟังก์ชันที่สนับสนุนการทำงานจริงของลูกค้าอย่างเหมาะสมและตรงเป้าหมายหรือไม่
2. Consistency (ความสอดคล้องกัน): Are there any requirement conflicts or contradictory constraints between different specifications?
ข้อกำหนดต่างๆ ไม่มีความขัดแย้งกันเองในระบบ เช่น กำหนด response time ขัดกับระบบความปลอดภัย
3. Completeness (ความสมบูรณ์ครบถ้วน): Are all necessary services, edge cases, and user constraints completely specified?
ระบุฟังก์ชัน ข้อจำกัด และกรณีเกิดข้อผิดพลาด (Exception/Error handling) ไว้ครบถ้วนทุกกรณี
4. Realism (ความเป็นไปได้จริง): Can the requirements be realistically implemented within the available budget, technology, and schedule?
สามารถพัฒนาได้จริงภายใต้งบประมาณ เทคโนโลยี และกรอบเวลาที่มีอยู่
5. Verifiability (ความสามารถในการทดสอบได้): Can each requirement be objectively and measurably tested and verified?
สามารถเขียน Test Case เพื่อตรวจสอบวัดผลได้อย่างเป็นรูปธรรม ไม่คลุมเครือ
(d) 3 ขั้นตอนกระบวนการจัดการการเปลี่ยนแปลง (Requirements Change Management Process)
Step 1: Problem Analysis and Change Specification -> Analyze the identified problem or change request to verify its validity and define precise change proposals.
ขั้นที่ 1 วิเคราะห์ปัญหาและระบุข้อกำหนดการเปลี่ยนแปลง: ตรวจสอบว่าปัญหาที่แจ้งมาถูกต้องหรือไม่ และร่างรายละเอียดการแก้ไข
Step 2: Change Analysis and Costing -> Assess the impact on system architecture, schedule, and cost using Traceability links to decide whether to accept the change.
ขั้นที่ 2 วิเคราะห์ผลกระทบและประเมินค่าใช้จ่าย: ประเมินว่าส่งผลกระทบต่อโมดูลอื่น งบประมาณ และเวลาเท่าใด เพื่อตัดสินใจอนุมัติ
Step 3: Change Implementation -> Modify the requirements document, system design, code, and test cases accordingly.
ขั้นที่ 3 ดำเนินการแก้ไข: ปรับแก้เอกสาร Requirements, งานออกแบบ, ซอร์สโค้ด และชุดทดสอบให้ตรงกัน
⭐ เทคนิคการจำ: เกณฑ์ 5 ข้อ ท่องจำด้วยคีย์เวิร์ด: V-C-C-R-V (Validity, Consistency, Completeness, Realism, Verifiability)

📖 Chapter 1: Introduction to Software Engineering

Chapter 1

1. นิยามและพื้นฐาน (Software Engineering Fundamentals)

  • Software: โปรแกรมคอมพิวเตอร์และเอกสารที่เกี่ยวข้อง (Documentation เช่น User manual, Requirement docs)
  • Software Engineering (SE): สาขาวิชาวิศวกรรมที่เกี่ยวข้องกับ ทุกแง่มุมของการผลิตซอฟต์แวร์ (All aspects of software production) ตั้งแต่การคิดความต้องการไปจนถึงการบำรุงรักษาหลังใช้งาน
  • CS vs SE vs System Engineering:
    • Computer Science: เน้นทฤษฎีและพื้นฐานทางคอมพิวเตอร์ (Theory & Fundamentals)
    • Software Engineering: เน้นการลงมือปฏิบัติจริงเพื่อสร้างและส่งมอบซอฟต์แวร์ที่มีประโยชน์ (Practicalities of developing useful software)
    • System Engineering: ครอบคลุมภาพรวมระบบทั้งหมด ทั้ง Hardware, Software, Process engineering (SE เป็นส่วนย่อยของ System Engineering)
  • 4 Fundamental Activities: ทุกกระบวนการพัฒนาซอฟต์แวร์ต้องมี 4 กิจกรรมนี้เสมอ:
    1) Software Specification (การกำหนดความต้องการ)
    2) Software Development (การออกแบบและเขียนโปรแกรม)
    3) Software Validation (การตรวจรับรองว่าตรงตามที่ลูกค้าต้องการ)
    4) Software Evolution (การปรับปรุงแก้ไขตามการเปลี่ยนแปลง)

2. ประเภทของผลิตภัณฑ์ซอฟต์แวร์ (Software Products)

ประเภทผลิตภัณฑ์ คำอธิบาย ใครเป็นเจ้าของ Specification? ตัวอย่าง
Generic Products
(ซอฟต์แวร์ทั่วไปในท้องตลาด)		 ระบบ Stand-alone ที่ผลิตออกมาขายให้ผู้ใช้งานทั่วไปที่ต้องการซื้อ ผู้พัฒนาซอฟต์แวร์ (Developer) เป็นคนกำหนดฟีเจอร์และการเปลี่ยนแปลง Microsoft Office, Photoshop, AutoCAD, OS
Customized Products
(ซอฟต์แวร์สั่งทำเฉพาะ)		 ระบบที่ถูกจ้างพัฒนาโดยลูกค้าเฉพาะรายเพื่อให้ตรงตามความต้องการขององค์กรตนเอง ลูกค้า (Customer) เป็นคนกำหนด Specification และสั่งให้ปรับแก้ ระบบควบคุมการจราจรทางอากาศ, ระบบธนาคารเฉพาะทาง, ระบบโรงพยาบาล

3. จรรยาบรรณวิศวกรซอฟต์แวร์ (ACM/IEEE Code of Ethics - 8 Principles)

วิศวกรซอฟต์แวร์ต้องมีความรับผิดชอบมากกว่าแค่ทักษะทางเทคนิค ต้องยึดมั่นในหลักการ 8 ข้อ:

1. PUBLIC: คำนึงถึงประโยชน์และความปลอดภัยของสาธารณะเป็นอันดับแรก
2. CLIENT & EMPLOYER: ทำงานเพื่อประโยชน์สูงสุดของลูกค้า/นายจ้าง โดยไม่ขัดต่อสาธารณะ
3. PRODUCT: ส่งมอบผลงานที่มีคุณภาพและมาตรฐานสูงสุดเท่าที่จะทำได้
4. JUDGMENT: รักษาความซื่อสัตย์และดุลยพินิจที่เป็นอิสระทางวิชาชีพ
5. MANAGEMENT: ผู้บริหารต้องส่งเสริมแนวทางการจัดการที่มีจริยธรรม
6. PROFESSION: เชิดชูเกียรติ ชื่อเสียง และความน่าเชื่อถือของวิชาชีพ
7. COLLEAGUES: ปฏิบัติต่อเพื่อนร่วมงานด้วยความยุติธรรมและเกื้อกูลกัน
8. SELF: พัฒนาการเรียนรู้ตลอดชีวิต (Lifelong learning) และยึดมั่นจริยธรรม

4. กรณีศึกษาประจำวิชา (4 Standard Case Studies)

  • 1. Personal Insulin Pump: ระบบสมองกลฝังตัว (Embedded Safety-critical System) คำนวณและฉีดอินซูลินอัตโนมัติตามระดับน้ำตาลในเลือด
  • 2. Mentcare System: ระบบข้อมูลผู้ป่วยสุขภาพจิตสำหรับคลินิก (Patient Information System) รองรับการทำงานแบบออฟไลน์/ออนไลน์และรายงานการรักษา
  • 3. Wilderness Weather Station: ระบบเก็บข้อมูลสภาพอากาศในพื้นที่ทุรกันดารผ่านเซนเซอร์และส่งข้อมูลผ่านดาวเทียม (Data Collection System)
  • 4. iLearn Digital Learning Environment: ระบบสภาพแวดล้อมการเรียนรู้ดิจิทัลแบบ Service-oriented เชื่อมต่อบริการการศึกษาหลากหลาย

⚙️ Chapter 2: Software Processes

Chapter 2

1. โมเดลการพัฒนาซอฟต์แวร์หลัก (Software Process Models)

  • Waterfall Model: โมเดลแบบวางแผนล่วงหน้า (Plan-driven) แบ่งเป็น 5 เฟสตามลำดับ: Requirements -> Design -> Implementation & Unit Testing -> Integration & System Testing -> Operation & Maintenance
  • Incremental Development: สลับทำงานพร้อมกัน (Interleaved) ระหว่าง Specification, Development, และ Validation เหมาะกับธุรกิจสมัยใหม่
  • Reuse-Oriented (Integration & Configuration): เน้นการประกอบจากระบบที่มีอยู่ (COTS) มี 5 ขั้นตอน:
    Requirements Specification ➔ Software Discovery & Evaluation ➔ Requirements Refinement ➔ Application System Configuration ➔ Component Adaptation & Integration

2. ลำดับขั้นการทดสอบ (Testing Stages) & V-Model

  • 1. Component Testing (Unit Testing): ทดสอบชิ้นส่วนย่อย/ฟังก์ชัน/ออบเจกต์แต่ละตัวอย่างเป็นอิสระ โดยโปรแกรมเมอร์
  • 2. System Testing: นำคอมโพเนนต์ทั้งหมดมาประกอบและทดสอบระบบในภาพรวม เพื่อดูคุณสมบัติร่วม (Emergent properties)
  • 3. Acceptance Testing / Customer Testing: ทดสอบด้วยข้อมูลจริงของลูกค้า เพื่อตรวจรับมอบงานว่าตรงตามความต้องการ

3. การรับมือกับการเปลี่ยนแปลง (Coping with Change) & SEI CMM Levels

  • Change Anticipation: คาดการณ์การเปลี่ยนแปลงล่วงหน้า เช่น ทำ System Prototype ให้ลูกค้าดูก่อนเริ่มสร้างจริง
  • Change Tolerance: ออกแบบกระบวนการให้รองรับการแก้ในราคาถูก เช่น ทำแบบ Incremental Delivery
  • Throw-away Prototyping: ตัวต้นแบบที่สร้างขึ้นเพื่อสำรวจ Requirement เมื่อเข้าใจแล้วต้อง "ทิ้งไป" ห้ามนำมาทำเป็นระบบจริงเพราะไม่มีโครงสร้างที่ดีพอ
  • 5 ระดับวุฒิภาวะกระบวนการ (SEI Capability Maturity Model - CMM):
    • Level 1 (Initial): ควบคุมไม่ได้ ไม่มีแบบแผน (Ad-hoc)
    • Level 2 (Repeatable / Managed): มีขั้นตอนการจัดการโปรเจกต์ที่ทำซ้ำได้
    • Level 3 (Defined): มีกระบวนการมาตรฐานที่บันทึกเป็นลายลักษณ์อักษรทั้งองค์กร
    • Level 4 (Quantitatively Managed): มีการวัดผลกระบวนการด้วยตัวเลขและสถิติเชิงปริมาณ
    • Level 5 (Optimizing): มีการปรับปรุงกระบวนการอย่างต่อเนื่อง

📝 Chapter 4: Requirements Engineering

Chapter 4

1. การจำแนกประเภทความต้องการ (Requirements Classification)

ประเภท Requirement นิยาม (Definition) คำสำคัญและตัวอย่าง
Functional Requirements
(ความต้องการเชิงหน้าที่)		 ระบุว่าระบบต้อง "ทำอะไรได้บ้าง" (What the system should do), บริการที่ระบบมี, การตอบสนองต่อ Input, และสิ่งที่ระบบ ต้องไม่ทำ ระบบต้องล็อกอินได้, ระบบต้องคำนวณราคาสินค้า, ระบบต้องส่ง SMS แจ้งเตือน
Non-Functional Requirements
(ความต้องการเชิงคุณลักษณะ)		 ระบุคุณสมบัติ ข้อจำกัด และประสิทธิภาพการทำงานของระบบ (How the system performs) มักกระทบต่อ Architecture ภาพรวม แบ่งเป็น 3 หมวด:
• Product: Usability, Speed, Memory, Reliability
• Organisational: Operational, Development standards
• External: Legislative (PDPA), Safety, Ethical
Domain Requirements
(ความต้องการเชิงโดเมน)		 ข้อกำหนดเฉพาะทางที่เกิดจากสภาพแวดล้อมทางธุรกิจหรือสาขาอาชีพนั้นๆ โดยตรง การเชื่อมต่อ Active Directory ของมหาลัย, การปฏิบัติตามกฎระเบียบสาธารณสุข HIPAA/PDPA, สูตรคำนวณภาษี
Constraints
(ข้อจำกัดโครงการ)		 ข้อจำกัดด้านเทคโนโลยี งบประมาณ ภาษา เครื่องมือ หรือเวลาในการพัฒนา ต้องพัฒนาด้วย Flutter, ฐานข้อมูลต้องอยู่บน Linux, งบไม่เกิน 200,000 บาท, ต้องเสร็จใน 3 เดือน

2. User Requirements vs. System Requirements

  • User Requirements: เขียนอธิบายด้วยภาษาธรรมชาติ (Natural language) และภาพรวมสำหรับลูกค้า/ผู้ใช้งานที่ไม่มีพื้นฐานเทคนิค
  • System Requirements: เอกสารมีโครงสร้างที่ระบุรายละเอียดฟังก์ชัน บริการ และข้อจำกัดทางเทคนิคอย่างละเอียด เพื่อให้นักพัฒนาและสถาปนิกนำไปสร้างจริง

3. รูปแบบการเขียนเอกสาร Requirements Specification

  • 1. Natural Language: ใช้ประโยคภาษาคนทั่วไป ใช้คำว่า shall สำหรับข้อบังคับ (Mandatory) และ should สำหรับข้อแนะนำ (Desirable)
  • 2. Structured Natural Language (Form-Based): เขียนลงในเทมเพลตมาตรฐาน ระบุ Function, Description, Inputs, Outputs, Action, Pre/Post-conditions
  • 3. Tabular Specification: ตารางแสดงเงื่อนไข-การกระทำ (Condition-Action Table) เหมาะกับระบบที่มีเงื่อนไขการตัดสินใจซับซ้อน
  • 4. Graphical Notation: แผนภาพ UML เช่น Use Case Diagram และ Sequence Diagram

Lecture Q&A
Q1: What are the key challenges facing software engineering? (ความท้าทายสำคัญที่ SE เผชิญอยู่คืออะไร?)
คำตอบ: ปัจจุบันซอฟต์แวร์มีความหลากหลายที่เพิ่มขึ้น (Increasing diversity), ต้องลดระยะเวลาส่งมอบงาน (Reduced delivery times), และต้องพัฒนาซอฟต์แวร์ที่เชื่อถือได้ (Developing trustworthy software)
Q2: What are the costs of software engineering? (ต้นทุนของวิศวกรรมซอฟต์แวร์มีอะไรบ้าง?)
คำตอบ: แบ่งเป็น 2 ส่วนหลักๆ คือ ต้นทุนการพัฒนา 60% และต้นทุนการทดสอบระบบ 40% และสำหรับซอฟต์แวร์สั่งทำเฉพาะ ต้นทุนในการปรับปรุงแก้ไข (Evolution) มักสูงกว่าต้นทุนการพัฒนาแรกเริ่ม
Q3: What are the best software engineering techniques and methods? (เทคนิคและวิธีวิศวกรรมซอฟต์แวร์ที่ดีที่สุดคืออะไร?)
คำตอบ: ไม่มีวิธีใดดีที่สุดสำหรับทุกงาน (No universal best method) ขึ้นอยู่กับประเภทของระบบ เช่น การพัฒนาเกมควรพัฒนาด้วยการสร้างต้นแบบ (Prototyping) ในขณะที่ระบบความปลอดภัยวิกฤต (Safety-critical) ต้องมีการจัดทำรายละเอียดที่สมบูรณ์และวิเคราะห์ได้ (Analyzable specification)
Q4: What differences has the web made to software engineering? (เว็บสร้างความเปลี่ยนแปลงอย่างไรต่อ SE?)
คำตอบ: ทำให้เกิดบริการซอฟต์แวร์รูปแบบใหม่ (Software Services / Cloud), เพิ่มความเป็นไปได้ในการพัฒนาระบบกระจายตัวสูง (Highly distributed service-based systems), และนำไปสู่ความก้าวหน้าด้านภาษาโปรแกรมและการนำซอฟต์แวร์กลับมาใช้ใหม่ (Software Reuse)
