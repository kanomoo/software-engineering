EXAM QUESTION 1 : FULL 4-WAY CLASSIFICATION (CASE: SMART LIBRARY)

Question 1: Comprehensive Requirements Classification for "ReadSmart" University Library & AI Kiosk System
[ภาษาไทย]: การจำแนกความต้องการ 4 ด้านสำหรับระบบตู้ยืมคืนหนังสืออัจฉริยะ "ReadSmart"

หัวข้อ: Chapter 4 (FR, NFR Breakdown, Domain, Constraints) & Practice-ReqEng Standard • คะแนนโดยประมาณ: 25 คะแนน
[English Problem Scenario]: "ReadSmart" University AI Library & Self-Checkout System
KMUTNB Central Library is introducing an automated smart library borrowing and inventory system named "ReadSmart". Students and faculty members can authenticate at self-service kiosks using either their RFID student ID card or facial recognition. The kiosk RFID multi-tag scanner must allow users to place up to 10 books on the scanning tray simultaneously and check out all items within 5 seconds without manual barcode scanning. The system must automatically calculate loan due dates (14 days for students, 30 days for faculty), print e-receipts, and send return reminder push notifications via the Line Official Account 3 days before the due date. If a book is overdue, the system shall compute late fines at 5 Baht/day and restrict further borrowing privileges until all outstanding fines are paid via PromptPay QR code. The kiosk user interface must be accessible for visually impaired users with an integrated text-to-speech audio guide. System transaction response time must be under 1.5 seconds under a load of 500 concurrent active users. The system must integrate seamlessly with the Library of Congress Classification (LCC) / Dewey Decimal catalog database and comply with Thailand's PDPA regarding biometric data storage. The kiosk client software must be developed in React and Electron, deployed on touch kiosks running Windows 11 IoT, with a budget not exceeding 350,000 Baht, and delivered within 3.5 months.
[คำแปลโจทย์ภาษาไทย]: หอสมุดกลาง มจพ. ต้องการพัฒนาระบบยืม-คืนหนังสืออัจฉริยะ "ReadSmart" นักศึกษาและอาจารย์สามารถยืนยันตัวตนที่ตู้ Kiosk ด้วยบัตรนักศึกษา RFID หรือระบบสแกนใบหน้า ถาดสแกน RFID ต้องอ่านหนังสือพร้อมกันได้สูงสุด 10 เล่มและทำรายการยืมเสร็จใน 5 วินาทีโดยไม่ต้องยิงบาร์โค้ดทีละเล่ม ระบบต้องคำนวณวันครบกำหนดคืนอัตโนมัติ (นักศึกษา 14 วัน / อาจารย์ 30 วัน) ส่ง e-receipt และแจ้งเตือนล่วงหน้า 3 วันผ่าน LINE Official หากเกินกำหนด ต้องคำนวณค่าปรับวันละ 5 บาท และระงับสิทธิ์การยืมจนกว่าจะสแกนจ่ายผ่าน PromptPay QR Code หน้าจอมีระบบอ่านออกเสียงสำหรับผู้บกพร่องทางการมองเห็น ระบบต้องตอบสนองใน 1.5 วินาที รองรับผู้ใช้พร้อมกัน 500 คน เชื่อมต่อระบบฐานข้อมูลบรรณานุกรมดิวอี้/LCC ข้อมูลชีวมิติสอดคล้องกับ PDPA พัฒนาด้วย React และ Electron บน Windows 11 IoT งบไม่เกิน 350,000 บาท เสร็จใน 3.5 เดือน
1. Functional Requirements (ความต้องการเชิงหน้าที่ — What the system shall do)
• The system shall authenticate users via RFID student/staff identity cards or facial recognition.
ระบบต้องยืนยันตัวตนผู้ใช้งานผ่านบัตรประจำตัว RFID หรือการสแกนใบหน้าได้
• The system shall scan and identify up to 10 books simultaneously on the RFID tray during a single checkout session.
ระบบต้องสามารถสแกนและระบุรายการหนังสือบนถาด RFID ได้พร้อมกันสูงสุด 10 เล่มในการยืมครั้งเดียว
• The system shall automatically calculate due dates (14 days for students, 30 days for faculty) and send Line push reminders 3 days before due date.
ระบบต้องคำนวณวันกำหนดส่งคืนอัตโนมัติตามประเภทสมาชิก และส่งข้อความแจ้งเตือนล่วงหน้า 3 วันผ่าน LINE Official
• The system shall calculate overdue fines at 5 Baht/day and process fine settlements via PromptPay QR Code.
ระบบต้องคำนวณค่าปรับกรณีคืนหนังสือเกินกำหนดวันละ 5 บาท และรองรับการชำระค่าปรับผ่าน PromptPay QR Code
• The system shall suspend borrowing privileges automatically for accounts with unpaid overdue fines.
ระบบต้องระงับสิทธิ์การยืมหนังสือชั่วคราวโดยอัตโนมัติหากผู้ใช้งานมียอดค่าปรับค้างชำระ
2. Non-Functional Requirements (ความต้องการเชิงคุณลักษณะ — How the system should perform)
• Usability (Product): The kiosk must complete the multi-book checkout transaction within 5 seconds, and provide an integrated Text-to-Speech audio guide for visually impaired users.
ด้านความง่ายในการใช้งาน (Usability): ตู้ Kiosk ต้องประมวลผลการยืมหนังสือเสร็จสิ้นภายใน 5 วินาที และมีระบบอ่านออกเสียง (Text-to-Speech) สำหรับผู้บกพร่องทางการมองเห็น
• Performance (Product): The system transaction response time shall be under 1.5 seconds during peak concurrent usage of 500 users.
ด้านประสิทธิภาพ (Performance): เวลาตอบสนองของระบบต้องไม่เกิน 1.5 วินาที เมื่อมีผู้ใช้งานพร้อมกัน 500 คน
• Security & Privacy (External/Legislative): User facial recognition biometric data must be encrypted and managed strictly in compliance with Thailand's PDPA laws.
ด้านความปลอดภัยและกฎหมาย (Security/External): ข้อมูลสแกนใบหน้า (Biometric Data) ต้องได้รับการเข้ารหัสและจัดเก็บตามกฎหมาย PDPA
3. Domain Requirements (ความต้องการเฉพาะด้านโดเมน)
• The system must integrate with the university library's Dewey Decimal Classification (DDC) / Library of Congress Classification (LCC) catalog database.
ระบบต้องเชื่อมต่อกับฐานข้อมูลระบบจัดหมวดหมู่หนังสือแบบดิวอี้ (DDC) หรือรัฐสภาอเมริกัน (LCC) ของหอสมุดมหาวิทยาลัย
• The system must support standardized RFID ISO 28560 data models for library item tagging.
ระบบต้องรองรับมาตรฐานการเข้ารหัสข้อมูลแท็ก RFID สำหรับห้องสมุดตามมาตรฐานสากล (ISO 28560)
4. Constraints (ข้อจำกัดของโครงการ)
• Kiosk client application must be built using React and Electron running on Windows 11 IoT Enterprise.
โปรแกรมตู้ Kiosk ต้องพัฒนาด้วย React และ Electron บนระบบปฏิบัติการ Windows 11 IoT Enterprise
• Total project budget must not exceed 350,000 Baht.
งบประมาณการพัฒนาทั้งหมดต้องไม่เกิน 350,000 บาท
• The system must be fully deployed and accepted within 3.5 months.
ระบบต้องพัฒนา ติดตั้ง และตรวจรับมอบให้แล้วเสร็จภายในเวลาไม่เกิน 3.5 เดือน
⭐ เทคนิคการตอบ: NFR ต้องระบุตัวเลขที่วัดผลได้ชัดเจน (5 seconds, 1.5 seconds, 500 users) ห้ามเขียนแค่ "ระบบต้องเร็ว"
EXAM QUESTION 2 : REQUIREMENTS AMBIGUITY & TESTABLE METRICS

Question 2: Resolving Requirements Ambiguity & Converting Vague Goals into Verifiable NFR Metrics
[ภาษาไทย]: การแก้ไขความคลุมเครือของความต้องการ และแปลง User Goal ให้เป็นตัวชี้วัด NFR เชิงปริมาณ

หัวข้อ: Chapter 4 (Requirements Imprecision, Non-Functional Metrics & Testability) • คะแนนโดยประมาณ: 20 คะแนน
[Problem Prompt]:
(a) Explain the fundamental difference between a "User Goal" and a "Verifiable Non-Functional Requirement".
(b) The following 4 requirement statements written by a client are vague, imprecise, and unverifiable. Analyze the flaw in each statement and rewrite each into a precise, verifiable requirement using quantitative metrics:
  1. "The mobile application shall be extremely fast and responsive for all users."
  2. "The system should be intuitive and user-friendly for elderly patients."
  3. "The medical database shall never crash and recover immediately if a power failure occurs."
  4. "The search feature shall search all information across the university."
[คำแปลโจทย์ภาษาไทย]:
(a) จงอธิบายความแตกต่างพื้นฐานระหว่าง "User Goal (เป้าหมายของผู้ใช้)" และ "Verifiable Non-Functional Requirement (ข้อกำหนดเชิงคุณลักษณะที่ตรวจสอบวัดผลได้)"
(b) ข้อกำหนด 4 ข้อต่อไปนี้ที่ลูกค้าเขียนมามีลักษณะ คลุมเครือ กำกวม และไม่สามารถทดสอบได้ (Unverifiable) จงวิเคราะห์จุดบกพร่องของแต่ละข้อ และ เขียนข้อกำหนดใหม่ให้มีความแม่นยำและสามารถวัดผลได้ด้วยตัวชี้วัดเชิงปริมาณ (Quantitative Metrics):
  1. "แอปพลิเคชันบนมือถือต้องทำงานได้อย่างรวดเร็วมากและตอบสนองทันใจสำหรับผู้ใช้ทุกคน"
  2. "ระบบควรจะใช้งานง่ายและเข้าใจได้ทันทีสำหรับผู้ป่วยสูงอายุ"
  3. "ฐานข้อมูลทางการแพทย์จะต้องไม่มีวันล่ม และต้องกู้คืนกลับมาได้ทันทีหากเกิดไฟฟ้าดับ"
  4. "ฟังก์ชันการค้นหาจะต้องค้นหาข้อมูลทั้งหมดทั่วทั้งมหาวิทยาลัยได้"
(a) ความแตกต่างระหว่าง "User Goal" และ "Verifiable Non-Functional Requirement"
• Goal (เป้าหมาย): A general intention or aspiration of the user/client (e.g., "The system should be user-friendly"). It expresses what the customer desires in broad terms, but cannot be objectively tested or verified by a software tester.
User Goal: ความตั้งใจหรือความปรารถนาทั่วไปของลูกค้า เช่น "ระบบต้องใช้ง่ายและรวดเร็ว" ซึ่งมีประโยชน์ในการสื่อสารเป้าหมายภาพรวม แต่ ไม่สามารถนำไปเขียน Test Case เพื่อทดสอบวัดผลได้
• Verifiable Non-Functional Requirement (ข้อกำหนดที่ตรวจสอบได้): A requirement statement structured using measurable, quantitative operational metrics (e.g., speed in seconds, training time in hours, error rate). A software engineer or QA tester can write an objective test pass/fail criterion to verify whether the system satisfies the specification.
Verifiable NFR: ข้อกำหนดที่ระบุเป็น ตัวเลขหรือเกณฑ์ชี้วัดเชิงปริมาณ (Metrics) ที่ชัดเจน ทำให้นักทดสอบระบบสามารถระบุได้แน่นอนว่าระบบ "ผ่าน (Pass)" หรือ "ไม่ผ่าน (Fail)" ตามข้อกำหนด
(b) การแก้ไขข้อกำหนดที่คลุมเครือให้เป็นเกณฑ์ที่วัดผลได้จริง (4 Rewrite Cases)
ข้อความเดิมที่คลุมเครือ (Vague Statement) จุดอ่อน/ความคลุมเครือ (Flaw / Ambiguity) ข้อกำหนดที่เขียนใหม่แบบวัดผลได้ (Verifiable Rewrite with Metrics)
1. "The mobile application shall be extremely fast and responsive for all users." คำว่า extremely fast และ responsive เป็นความรู้สึกส่วนบุคคล ไม่มีตัวเลขวัดเวลาหรือจำนวนผู้ใช้ Rewrite:
• The mobile application UI shall render search results within 1.5 seconds under 4G/5G network conditions.
• The server shall maintain response times under 2.0 seconds for up to 1,000 concurrent active users.
2. "The system should be intuitive and user-friendly for elderly patients." คำว่า intuitive และ user-friendly ทดสอบไม่ได้ ไม่รู้ว่าวัดจากอะไร Rewrite:
• Elderly users (≥ 60 years) shall be able to complete a doctor appointment booking within 3 minutes after 10 minutes of initial instruction, with an operational error rate not exceeding 5%.
3. "The medical database shall never crash and recover immediately if a power failure occurs." คำว่า never crash เป็นไปไม่ได้ในทางวิศวกรรม (Unrealistic) และ immediately ไม่ระบุหน่วยเวลา Rewrite:
• The system shall achieve 99.95% availability during clinic hours (Mean Time To Failure: MTTF > 5,000 hours).
• In the event of a power outage, the database shall restore to the last consistent checkpoint with a Mean Time To Recovery: MTTR ≤ 30 seconds, with zero data loss (RPO = 0).
4. "The search feature shall search all information across the university." คำว่า search all information มีความกำกวม (Ambiguous) ไม่ชัดเจนว่าค้นหาเอกสาร, ทะเบียนนักศึกษา, คลังพัสดุ หรือข้อมูลบุคคล Rewrite:
• The search engine shall search across the University Central Student Database, Library Catalog, and Course Syllabus Repository using keywords matching title, author, or student ID, returning relevant indexed results within 1.0 second.
⭐ เกณฑ์การให้คะแนน: คะแนนเต็มจะให้เมื่อระบุทั้ง (1) ตัวชี้วัดเชิงปริมาณ (Seconds, Hours, %, Users) และ (2) เงื่อนไขในการทดสอบที่ชัดเจน
EXAM QUESTION 3 : STAKEHOLDER ELICITATION & 5-PART SCENARIO DESIGN

Question 3: Stakeholder Analysis, Elicitation Pitfalls & Scenario Specification
[ภาษาไทย]: การวิเคราะห์ Stakeholder, ปัญหาของการสัมภาษณ์ และการเขียน Scenario ครบ 5 องค์ประกอบ

หัวข้อ: Chapter 4 (Elicitation Challenges, Interviews vs Ethnography, 5 Scenario Elements) • คะแนนโดยประมาณ: 20 คะแนน
[Problem Prompt]: "TeleMed Care" Remote Consultation & E-Prescription System
(a) Identify at least 6 key Stakeholders (Internal and External) and their roles for the "TeleMed Care" system.
(b) Explain why relying solely on Interviews often leads to incomplete requirements, and how Ethnography solves this problem.
(c) Write a complete User Scenario for a patient conducting a video consultation and receiving an electronic prescription. Your scenario MUST explicitly include all 5 mandatory components:
  1. Starting situation / Initial state
  2. Normal flow of events
  3. What can go wrong (Exception / Error handling)
  4. Other concurrent activities
  5. State on completion
[คำแปลโจทย์ภาษาไทย]:
ระบบการแพทย์ทางไกลและการจ่ายยาอิเล็กทรอนิกส์ "TeleMed Care"
(a) จงระบุ ผู้มีส่วนได้ส่วนเสียหลักอย่างน้อย 6 กลุ่ม (ทั้ง Internal และ External) พร้อมอธิบายบทบาทหน้าที่และความรับผิดชอบในระบบ TeleMed Care
(b) จงอธิบายเหตุผลว่าทำไมการพึ่งพาเฉพาะ การสัมภาษณ์ (Interviews) จึงมักทำให้ได้ข้อมูลความต้องการที่ไม่ครบถ้วน และเทคนิค Ethnography (การสังเกตการณ์ในสถานที่จริง) เข้ามาช่วยแก้ปัญหานี้ได้อย่างไร
(c) จงเขียน User Scenario (สถานการณ์การใช้งานของผู้ใช้) ที่สมบูรณ์สำหรับกรณี "คนไข้เข้ารับการตรวจผ่านวิดีโอคอลและรับใบสั่งยาอิเล็กทรอนิกส์" โดยข้อเขียนของคุณต้องมี 5 องค์ประกอบบังคับ อย่างชัดเจน:
1. Starting situation (สถานะเริ่มต้น)
2. Normal flow of events (ลำดับขั้นตอนปกติ)
3. What can go wrong (กรณีเกิดข้อผิดพลาด / ข้อยกเว้น)
4. Other concurrent activities (กิจกรรมอื่นที่ดำเนินอยู่คู่ขนาน)
5. State on completion (สถานะเมื่อสิ้นสุดขั้นตอน)
(a) ตารางวิเคราะห์ผู้มีส่วนได้ส่วนเสีย 6 กลุ่ม (TeleMed Care Stakeholders & Roles)
Stakeholder ประเภท บทบาทหน้าที่และความต้องการในระบบ (Role & Responsibility)
1. Consulting Doctors Internal ตรวจรักษาผ่านวิดีโอคอล ดูประวัติการรักษาในอดีต สั่งจ่ายยาอิเล็กทรอนิกส์ (E-Prescription) และบันทึกคำวินิจฉัย
2. Clinic Nurses & Triage Staff Internal คัดกรองอาการผู้ป่วยเบื้องต้น ตรวจสอบคิวออนไลน์ และจัดห้องตรวจเสมือนจริงให้แพทย์
3. Patients (End Users) External จองคิวนัดหมาย เข้ารับการตรวจผ่านวิดีโอบนสมาร์ตโฟน ชำระเงินค่ารักษา และเลือกรับยาที่บ้านหรือร้านยาใกล้บ้าน
4. Partner Pharmacists (ร้านยาเครือข่าย) External รับใบสั่งยาอิเล็กทรอนิกส์ ตรวจสอบการแพ้ยา จัดเตรียมยา และยืนยันการส่งมอบยาให้ผู้ป่วยหรือไรเดอร์
5. Hospital IT Security Administrator Internal ดูแลระบบเซิร์ฟเวอร์ จัดการการเข้ารหัสการสื่อสารวิดีโอ (End-to-End Encryption) และสำรองข้อมูลเวชระเบียน

• Why Interviews are Incomplete:
1. Domain Jargon: Stakeholders use specialized technical language that requirements engineers misunderstand.
2. Tacit Knowledge (ความรู้ฝังลึก): Users are so familiar with their daily work that they forget to mention critical habits, workarounds, and implicit rules.
3. Organizational Politics: Interviewees often describe "how work ought to be done according to rules" rather than "how work is actually done".
เหตุผลที่การสัมภาษณ์มักได้ข้อมูลไม่ครบ: ผู้ใช้มี "ความรู้ความเคยชิน (Tacit Knowledge)" ที่คิดว่าเป็นเรื่องธรรมดาจึงลืมเล่า, การใช้ศัพท์เฉพาะทางที่เข้าใจไม่ตรงกัน, และผู้ปฏิบัติงานมักบอกขั้นตอนตามอุดมคติในคู่มือมากกว่าวิธีที่ทำจริง
• How Ethnography Solves This: Ethnographers immerse themselves in the actual work environment, observing daily workflows without relying on user verbal descriptions. This reveals implicit social dynamics, practical workarounds, and inter-departmental interactions.
วิธีที่ Ethnography แก้ปัญหา: นักวิเคราะห์เข้าไปสังเกตการณ์ในสถานที่จริงด้วยตาตนเอง ทำให้มองเห็นขั้นตอนจริง วิธีแก้ปัญหาเฉพาะหน้า และปฏิสัมพันธ์ระหว่างแผนกที่ไม่มีเขียนไว้ในเอกสารใดๆ

(a) 5 เกณฑ์การตรวจสอบความต้องการ (V-C-C-R-V) พร้อมตัวอย่างข้อผิดพลาด
เกณฑ์การตรวจสอบ (Check) นิยามและเป้าหมาย (Definition & Goal) ตัวอย่างข้อผิดพลาดที่ตรวจพบ (Example Error Detected)
1. Validity
(ความสมเหตุสมผล)		 ระบบมีฟังก์ชันที่ตรงกับความต้องการและวิธีปฏิบัติงานจริงของลูกค้าหรือไม่ ระบุให้แพทย์ต้องพิมพ์ชื่อยาทุกตัวด้วยตนเอง ทั้งที่งานจริงต้องการเมนูคลิกเลือกยาสำเร็จรูปเพื่อความรวดเร็ว

(ความสอดคล้องกัน)		 ไม่มีข้อกำหนดใดในเอกสารที่ขัดแย้งหรือค้านกันเอง หน้า 5 ระบุว่า "ระบบต้องไม่อนุญาตให้บุคคลภายนอกเข้าถึงเวชระเบียน" แต่หน้า 20 ระบุว่า "อนุญาตให้นักวิจัยภายนอกดาวน์โหลดไฟล์ข้อมูลคนไข้ได้อิสระ"

5. Verifiability
(ความสามารถในการทดสอบได้)		 ทุกข้อกำหนดต้องเขียนขึ้นเพื่อให้สามารถออกแบบชุดทดสอบเพื่อวัดผลผ่าน/ไม่ผ่านได้อย่างชัดเจน เขียนว่า "ระบบต้องใช้งานง่ายและสวยงาม" (ทดสอบไม่ได้) ➔ ต้องแก้เป็น "ผู้ใช้ใหม่ 90% ทำรายการเสร็จใน 2 นาทีโดยไม่ผิดพลาด"
(b) การสืบย้อนความต้องการ (Traceability) 3 รูปแบบ
• Definition of Traceability: The ability to discover the relationship between requirements, their sources, and system design components throughout the project lifecycle.
ความหมายของ Traceability: ความสามารถในการติดตามความเชื่อมโยงระหว่างความต้องการ แหล่งที่มาของความต้องการ และชิ้นส่วนการออกแบบของระบบ เพื่อช่วยในการวิเคราะห์ผลกระทบเมื่อเกิดการเปลี่ยนแปลง
1. Source Traceability: Links requirements to the specific stakeholders, business goals, or regulations that originally requested them (Who proposed this requirement?).
การสืบย้อนแหล่งที่มา (Source): เชื่อมโยง Requirement กลับไปยังตัวบุคคล, ลูกค้า, หรือกฎหมายที่เป็นต้นกำเนิดของข้อกำหนดนั้น
2. Requirements Traceability (Req-to-Req): Links dependent requirements to each other (Which requirements are affected if requirement X changes?).
การสืบย้อนระหว่างความต้องการ (Req-to-Req): บันทึกความสัมพันธ์ระหว่าง Requirement ด้วยกันเอง เพื่อดูว่าถ้าแก้ข้อนี้ จะกระทบกับข้อกำหนดอื่นข้อใดบ้าง
3. Design Traceability: Links requirements to the specific architectural components, modules, source code files, and test cases that implement them.
การสืบย้อนสู่งานออกแบบ (Design): เชื่อมโยง Requirement แต่ละข้อไปยังโมดูลสถาปัตยกรรม, ซอร์สโค้ดไฟล์, และ Test Cases ที่สร้างขึ้นเพื่อตอบสนองข้อกำหนดนั้น
(c) 3 ขั้นตอนกระบวนการจัดการการเปลี่ยนแปลง (Requirements Change Management Process)
Stage 1: Problem Analysis and Change Specification
An incoming change request is evaluated to verify if the reported problem is genuine. A formal proposed change specification is drafted.
ขั้นที่ 1 วิเคราะห์ปัญหาและระบุรายละเอียดการเปลี่ยนแปลง: ตรวจสอบว่าคำขอแก้ไขที่แจ้งเข้ามามีเหตุผลสมควรจริงหรือไม่ และร่างข้อกำหนดการเปลี่ยนแปลงอย่างเป็นทางการ
Stage 2: Change Analysis and Costing
Using Traceability links, the change impact on system architecture, code, test cases, schedule, and cost is thoroughly assessed. The Change Control Board (CCB) decides whether to accept, reject, or defer the change.
ขั้นที่ 2 วิเคราะห์ผลกระทบและประเมินค่าใช้จ่าย: ใช้ข้อมูล Traceability ตรวจสอบผลกระทบต่องานส่วนอื่น งบประมาณ และเวลาส่งมอบ เพื่อให้คณะกรรมการ (CCB) ตัดสินใจอนุมัติหรือปฏิเสธ
