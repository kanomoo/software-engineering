🔍 ตอนที่ 1: เจอโจทย์พารากราฟภาษาอังกฤษยาวๆ ต้องดูยังไง? (3-Step Scanner Engine)

ในข้อสอบจริง อาจารย์จะให้ เนื้อเรื่องสถานการณ์ (Scenario) เป็นภาษาอังกฤษยาว 1 หน้ากระดาษมาให้อ่าน สิ่งที่นักศึกษา 90% พลาดคือ "พยายามอ่านและแปลทุกคำตั้งแต่ต้นจนจบ" ทำให้เสียเวลาและสับสน

⚡ กฎทอง 3 สเต็ปในการสแกนข้อสอบ (จำสูตรนี้ไปใช้ได้ทันที):
  1. Step 1 (ล่าประธาน + กริยา = FR): ประโยคไหนมีคำว่า allow / can / able to / shall / register / search / add to cart / calculate / generate report $\rightarrow$ นั่นคือ Functional Requirement (ระบบทำอะไรได้)
  2. Step 2 (ล่าตัวเลข + คุณภาพ = NFR): ประโยคไหนมี ตัวเลข, วินาที (seconds), ผู้ใช้พร้อมกัน (concurrent users), อัตราความพร้อมใช้งาน (99.9%), การเข้ารหัส (SSL/TLS), ใช้งานง่าย (user-friendly) $\rightarrow$ นั่นคือ Non-Functional Requirement (ระบบต้องทำงานได้ดีแค่ไหน)
  3. Step 3 (ล่ากฎหมายเฉพาะวงการ = Domain & ล่าข้อผูกมัด = Constraint):
    • เจอ PDPA / HIPAA / HStan-03 / สองภาษา (Thai & English) / เชื่อมระบบบัญชีมหาวิทยาลัย $\rightarrow$ Domain Requirement
    • เจอ ภาษาโปรแกรม (Flutter, React, Laravel) / OS (Linux, Windows) / งบประมาณ (Baht) / กำหนดเวลา (Months) $\rightarrow$ Constraint (ข้อจำกัด)
ประเภท Requirement คำถามที่ใช้ถามตัวเอง คีย์เวิร์ดภาษาอังกฤษที่สังเกตได้ทันที (Keywords) สูตรประโยคในการเขียนตอบ
1. Functional Requirement (FR) ระบบต้อง "ทำอะไรได้บ้าง" ให้กับผู้ใช้? (ฟังก์ชัน/ปุ่ม/ระบบงาน) allow, log in, register, browse, add to cart, calculate, send email, notify, view, search The system shall allow [User] to [Action]...
(ระบบต้องอนุญาตให้ [ใคร] สามารถ [ทำอะไร]...)
2. Non-Functional Requirement (NFR) ระบบต้องทำงาน "มีคุณภาพและเร็ว/เสถียรแค่ไหน"? within X seconds, 1000 concurrent users, 99.9% uptime, SSL/TLS, encrypted, within 5 minutes The system shall [perform with metric X under condition Y]...
(ระบบต้องตอบสนองภายใน [X วินาที / รองรับ Y คน]...)
3. Domain Requirement เป็น "กฎเกณฑ์เฉพาะทางของธุรกิจ/วงการนี้" หรือไม่? PDPA, HIPAA, Medical standards, Thai & English support, University account sync, LCC/Dewey catalog The system must comply with [Domain Law/Standard]...
(ระบบต้องสอดคล้องตามกฎระเบียบ [ของวงการนั้นๆ]...)
4. Constraint (ข้อจำกัด) เป็น "กรอบกติกาบังคับตายตัว" ด้านเทคโนโลยี งบ หรือเวลาหรือไม่? Framework (Flutter, Laravel), Server (Linux), Budget (X Baht), Deadline (within X months) The system must be developed using [Tech] / completed within [Time] / under [Budget]

👥 ตอนที่ 2: Stakeholder คืออะไร? ทำไมไม่รู้เรื่องเลย แล้วต้องตอบตารางยังไง?

💡 เข้าใจ Stakeholder ใน 1 นาที (จำง่ายๆ):
Stakeholder (ผู้มีส่วนได้ส่วนเสีย) คือ "มนุษย์หรือกลุ่มคน หรือองค์กร ทุกคนที่ได้รับผลกระทบ ได้ประโยชน์ เสียประโยชน์ หรือต้องเข้ามายุ่งเกี่ยวกับระบบนี้"
จำไว้ว่า Stakeholder ไม่ได้มีแค่คนใช้โปรแกรม (User) เท่านั้น! แต่รวมถึงคนจ่ายเงิน คนคุมกฎหมาย โปรแกรมเมอร์ และคนขายของด้วย!

1. การแบ่งประเภท Stakeholder 2 ฝั่ง (Internal vs External)

🏢 1. Internal Stakeholders (คนในองค์กร)

คือคนที่ทำงานอยู่ ข้างในบริษัท/คลินิก/มหาวิทยาลัย หรือเป็นทีมสร้างระบบ:

  • Project Sponsor / เจ้าของร้าน / ผู้บริหาร: คนจ่ายเงินอนุมัติโครงการ อยากได้ระบบเพื่อเพิ่มยอดขายหรือลดต้นทุน
  • End Users ภายใน (พนักงาน, หมอ, พยาบาล, คนขับรถ): คนที่ต้องนั่งหน้าจอโปรแกรมเพื่อทำงานทุกวัน
  • Software Developers / Designers / IT Admin: คนเขียนโค้ด ออกแบบหน้าจอ และดูแลเซิร์ฟเวอร์

🌍 2. External Stakeholders (คนนอกองค์กร)

คือคนที่อยู่ ภายนอกองค์กร แต่มาเกี่ยวข้องหรือได้รับผลกระทบ:

  • Customers / Patients / Students (ลูกค้า/คนไข้/นักศึกษา): คนภายนอกที่โหลดแอปมาสั่งอาหาร จองคิว หรือยืมหนังสือ
  • Regulators (หน่วยงานกำกับดูแล): กระทรวงสาธารณสุข, กฎหมาย PDPA, อย., แพทยสภา (ต้องตรวจสอบความถูกต้องตามกฎหมาย)
  • Third-Party Vendors / Payment Providers: ธนาคาร, บริษัท PromptPay/บัตรเครดิต, ร้านขายยาคู่สัญญา

2. ตาราง Stakeholder แต่ละช่องคืออะไร? ต้องเขียนอะไรลงไปบ้าง?

เวลาข้อสอบให้เขียนตาราง Stakeholder ให้แบ่งเป็น 3 คอลัมน์มาตรฐานนี้เสมอ:

ช่องที่ 1: Stakeholder (ชื่อกลุ่มคน) ช่องที่ 2: Category (ประเภท) ช่องที่ 3: Role & Responsibility (บทบาทหน้าที่ในระบบ)
เขียนชื่อบทบาทของคนนั้น
(เช่น Clinic Owner, Doctor, Patient, Software Developer, Payment Provider)		 ระบุว่าเป็นคนในหรือคนนอก
• Internal (คนใน/ทีมงาน)
• External (คนนอก/ลูกค้า/กฎหมาย) 		เขียนว่าเขา "ทำอะไรกับระบบ" หรือ "ต้องการอะไรจากระบบ"
สูตรการเขียนช่องนี้:
• ถ้าเป็นผู้ใช้: ใช้ระบบเพื่อทำอะไร (เช่น จองคิว, สั่งซื้อ, ดูประวัติ)
• ถ้าเป็นเจ้าของ: ใช้ระบบดูรายงานยอดขาย และควบคุมทิศทางธุรกิจ
• ถ้าเป็น Dev: พัฒนา ออกแบบหน้าจอ และดูแลความปลอดภัยระบบ
• ถ้าเป็นระบบจ่ายเงิน: ประมวลผลธุรกรรมทางการเงินให้สำเร็จและปลอดภัย

Case 1: "FreshMart" E-commerce Website (หน้า 1-2 ของ PDF)

[English Scenario]:
FreshMart is a new online grocery store aiming to deliver fresh vegetables, fruits, and daily essentials directly to customers in Bangkok. The store owner, Ms. Supansa, wants to launch an easy-to-use website for her customers to order products online and receive deliveries promptly.

[คำแปลไทยแบบละเอียด]:
FreshMart เป็นร้านขายของชำออนไลน์แห่งใหม่ที่ต้องการส่งผักสด ผลไม้ และของใช้จำเป็นในชีวิตประจำวันตรงถึงลูกค้าในกรุงเทพฯ คุณสุพรรษาเจ้าของร้านต้องการเปิดตัวเว็บไซต์ที่ใช้งานง่าย เพื่อให้ลูกค้าสั่งซื้อสินค้าออนไลน์และได้รับการจัดส่งที่รวดเร็วตรงเวลา

ถอดรหัสความต้องการทั้ง 4 ด้าน (Model Breakdown):

ประเภท ข้อกำหนดที่ถอดได้ (EN / TH) เหตุผลที่จัดอยู่ในหมวดนี้
1. Functional Requirements (FR) 1. ลงทะเบียนและล็อกอินด้วย Email / Password
2. แสดงรายการสินค้าแยกหมวดหมู่ชัดเจน (ผัก, ผลไม้, เบเกอรี่)
3. เพิ่ม แก้ไข และลบสินค้าในตะกร้า (Cart Management)
4. คำนวณและแสดงราคารวมในตะกร้าสินค้า
5. เลือกรอบเวลาจัดส่ง (Delivery Time Slots)
6. รับชำระเงินผ่านบัตรเครดิต/เดบิต และ Mobile Banking
7. ส่งอีเมลยืนยันคำสั่งซื้อพร้อมรายละเอียดการจัดส่งอัตโนมัติ 		เป็นสิ่งที่ระบบ "ต้องทำหน้าที่ได้" (Functions & Features) ให้กับผู้ใช้งาน
2. Non-Functional Requirements (NFR) • Usability: สั่งซื้อครั้งแรกเสร็จในเวลาไม่เกิน 10 นาที, Responsive รองรับ Mobile & Desktop
• Performance: ตอบสนองการค้นหา/เพิ่มสินค้าภายใน 3 วินาที, รองรับผู้ใช้พร้อมกัน 500 คน (Concurrent Users)
• Reliability: พร้อมใช้งาน 99.9% Uptime ในช่วงเวลาเร่งด่วน (เย็นและวันหยุด)
• Security: เข้ารหัสข้อมูลลูกค้าและการเงินด้วย SSL/TLS, Backup ฐานข้อมูลทุกวันเวลา 02:00 น. 		เป็นเกณฑ์ชี้วัด "คุณภาพ ประสิทธิภาพ และความปลอดภัย" ที่มีตัวเลขวัดผลได้ชัดเจน (3s, 500 users, 99.9%)
3. Domain Requirements 1. ต้องปฏิบัติตามกฎหมายคุ้มครองข้อมูลส่วนบุคคลของไทย (PDPA)
2. ต้องรองรับการแสดงผลสินค้า 2 ภาษา (ภาษาไทย และ ภาษาอังกฤษ) เพื่อรองรับลูกค้าหลากหลายกลุ่มในกรุงเทพฯ 		เป็นกฎหมายเฉพาะของประเทศ (PDPA) และบริบทธุรกิจค้าปลีกในพื้นที่กรุงเทพฯ (Bilingual)
4. Constraints (ข้อจำกัด) • Framework: ต้องพัฒนาด้วย Laravel PHP Framework (เพราะหาผู้เชี่ยวชาญในท้องถิ่นได้ง่าย)
• Hosting: ต้องรันบน Linux Server ที่ตั้งอยู่ในประเทศไทย
• Budget: งบประมาณพัฒนาต้องไม่เกิน 200,000 บาท
• Deadline: ต้องพัฒนาเสร็จและเปิดใช้งานได้ภายใน 3 เดือน 		เป็นข้อจำกัดตายตัวด้านเทคโนโลยี (Laravel, Linux), งบประมาณ (200k), และเวลา (3 เดือน)

Case 2: KMUTNB Cafeteria Food Ordering Mobile App (หน้า 3-4 ของ PDF)

[English Scenario]:
The KMUTNB University Cafeteria recently decided to enhance their food ordering experience by developing a mobile application for students. They reached out to a software development team and clearly stated their needs: students should log in easily with their university email. Once logged in, students would browse a digital menu, selecting their meals and adding them to a cart. The app would instantly calculate the total price and display an order summary, allowing students to conveniently pay through mobile banking or digital wallets. Each time an order is placed, cafeteria staff would immediately receive notifications, enabling quick and efficient service. Moreover, students would always see a clear estimated pickup time for their meals. To ensure smooth operations, the university required that the app handle at least 1,000 concurrent users without performance degradation. Furthermore, user data security must strictly follow the university’s data privacy policies. Lastly, to ensure broad accessibility among students, the cafeteria requested that the app be compatible with both Android and iOS devices and be ready for use within two months.

[คำแปลไทยแบบประโยคต่อประโยค]:
โรงอาหารมหาวิทยาลัยเทคโนโลยีพระจอมเกล้าพระนครเหนือ (มจพ.) ตัดสินใจยกระดับการสั่งอาหารโดยพัฒนาแอปมือถือสำหรับนักศึกษา โดยมีความต้องการดังนี้: นักศึกษาเข้าสู่ระบบด้วยอีเมลมหาวิทยาลัย เมื่อล็อกอินแล้วสามารถดูเมนูดิจิทัล เลือกอาหาร และเพิ่มลงตะกร้า แอปจะคำนวณราคารวมทันทีและแสดงสรุปคำสั่งซื้อ รองรับการจ่ายผ่าน Mobile Banking หรือกระเป๋าเงินดิจิทัล ทุกครั้งที่มีออเดอร์ เจ้าหน้าที่โรงอาหารจะได้รับการแจ้งเตือนทันที นักศึกษาจะเห็นเวลาประมาณการรับอาหารอย่างชัดเจน ระบบต้องรองรับผู้ใช้พร้อมกันอย่างน้อย 1,000 คนโดยไม่อืด ข้อมูลส่วนบุคคลต้องปลอดภัยตามระเบียบความเป็นส่วนตัวของมหาวิทยาลัย แอปต้องรองรับทั้ง Android และ iOS และพร้อมใช้งานภายใน 2 เดือน

การจำแนกคำตอบ 4 ด้าน (Answer Breakdown):

Functional Requirements
  • ล็อกอินด้วยอีเมลมหาวิทยาลัย (@kmutnb.ac.th)
  • ดูเมนูอาหาร และเพิ่มลงตะกร้าสินค้า
  • คำนวณราคารวมและแสดงสรุปก่อนชำระเงิน
  • ชำระเงินผ่าน Mobile Banking หรือ Digital Wallet
  • ส่ง Notification แจ้งเตือนพนักงานโรงอาหารทันทีที่มีออเดอร์ใหม่
  • แสดงเวลานัดรับอาหารโดยประมาณ (Estimated Pickup Time)
Non-Functional Requirements
  • Performance: รองรับผู้ใช้งานพร้อมกันอย่างน้อย 1,000 คน (Concurrent Users) โดยระบบไม่หน่วง
  • Security: ป้องกันข้อมูลส่วนบุคคลตามนโยบาย Data Privacy ของมหาวิทยาลัย
  • Usability: ใช้งานง่าย นักศึกษาเรียนรู้การใช้งานพื้นฐานได้รวดเร็ว
Domain Requirements
  • ต้องเชื่อมต่อกับระบบฐานข้อมูลบัญชีผู้ใช้ของมหาวิทยาลัย (University SSO / Active Directory)
  • ปฏิบัติตามกฎระเบียบและนโยบายความเป็นส่วนตัวของ มจพ. (University Data Privacy Policy)
Constraints (ข้อจำกัด)
  • Platform: ต้องรันได้ทั้งระบบปฏิบัติการ Android และ iOS
  • Timeline: พัฒนาและเปิดใช้งานได้ภายในระยะเวลาไม่เกิน 2 เดือน

"เมื่อลูกค้าล็อกอินแล้ว พวกเขาจะเห็นเมนูพิซซ่าทั้งหมดของร้าน พร้อมรูปภาพและราคา" FR (ฟังก์ชันระบบ) The system shall display the full pizza menu with clear photos and prices. (ระบบต้องแสดงรายการเมนูพิซซ่าพร้อมรูปภาพและราคา)
"ลูกค้าสามารถเลือกขนาด แป้ง และท็อปปิ้งของพิซซ่าที่ต้องการ แล้วใส่ในตะกร้าสินค้าได้ง่ายๆ" FR (ฟังก์ชันระบบ) Customers shall be able to customize pizza (size, crust, toppings) and add items to the cart. (ลูกค้าสามารถเลือกขนาด แป้ง ท็อปปิ้ง และเพิ่มลงตะกร้า)
"แอปต้องคำนวณราคาทั้งหมดพร้อมแสดงสรุปรายการสั่งซื้อให้ดูอย่างชัดเจน" FR (ฟังก์ชันระบบ) The system shall calculate the total price and display an order summary. (ระบบต้องคำนวณราคารวมและแสดงสรุปการสั่งซื้อ)
"ระบบต้องรองรับการชำระเงินทั้งแบบโอนผ่านแอปธนาคาร และการจ่ายผ่านบัตรเครดิต" FR (ฟังก์ชันระบบ) The system shall support payments via mobile banking transfer and credit cards. (ระบบต้องรองรับการจ่ายเงินผ่าน Mobile Banking และบัตรเครดิต)
"เมื่อชำระเงินเรียบร้อย แอปต้องส่งใบเสร็จยืนยันการสั่งซื้อให้ลูกค้าผ่านอีเมลทันที" FR (ฟังก์ชันระบบ) The system shall automatically send an order confirmation receipt via email. (ระบบต้องส่งใบเสร็จยืนยันคำสั่งซื้อทางอีเมลอัตโนมัติ)
"ลูกค้าใหม่ควรจะสามารถสั่งซื้อพิซซ่าครั้งแรกเสร็จภายในเวลาไม่เกิน 5 นาที" NFR (Usability) Usability: First-time users shall be able to complete their order within 5 minutes. (ผู้ใช้ใหม่สั่งซื้อเสร็จใน 5 นาที)
"แอปต้องตอบสนองเร็ว ลูกค้าคลิกเมนูใดต้องแสดงผลไม่เกิน 2 วินาที" NFR (Performance) Performance: The application shall load and respond to menu selections within 2 seconds. (ตอบสนองการคลิกเมนูใน 2 วินาที)
"แอปต้องสามารถรองรับลูกค้าที่สั่งพร้อมกันได้มากถึง 300 คนโดยไม่เกิดอาการช้า" NFR (Scalability) Performance/Scalability: The system shall handle at least 300 concurrent users without slowdown. (รองรับผู้ใช้พร้อมกัน 300 คน)
"ระบบต้องเก็บข้อมูลลูกค้าอย่างปลอดภัยตามกฎหมาย PDPA ข้อมูลการเงินต้องเข้ารหัส" NFR (Security) & Domain Security: All financial transactions must be encrypted. Comply strictly with PDPA regulations. (เข้ารหัสข้อมูลการเงินและทำตาม PDPA)
"แอปต้องสามารถทำรายงานยอดขายประจำวันได้ รวมถึงรายงานสินค้าที่ลูกค้านิยมสั่งมากที่สุด" Domain Requirement Domain Application: The system shall generate daily sales reports and popular menu analysis for inventory management. (รายงานยอดขายประจำวันและเมนูยอดนิยมเพื่อบริหารสต็อก)
"ทีมพัฒนาต้องใช้ภาษา Flutter ในการเขียนแอป เพื่อรองรับทั้ง Android และ iOS ด้วยแอปเดียว" Constraint (Tech) Constraint: The app must be developed using the Flutter framework to support both Android and iOS. (ใช้ Flutter รองรับ Android/iOS)
"แอปนี้จะต้องพร้อมให้บริการลูกค้าได้ภายในเวลาไม่เกิน 3 เดือนเท่านั้น" Constraint (Time) Constraint: The system must be fully developed and ready to launch within 3 months. (เสร็จใน 3 เดือน)

Case 4: "ReadSmart" Online Bookstore (หน้า 7-8 ของ PDF — การวิเคราะห์ Stakeholder)

[English Scenario]:
"ReadSmart" is an online bookstore that sells printed books and e-books. Customers can browse titles, read reviews, and place orders for home delivery or instant e-book download. The business wants to develop a new website and mobile app to improve customer experience and streamline internal operations.

[คำแปลไทย]:
"ReadSmart" เป็นร้านหนังสือออนไลน์ที่จำหน่ายทั้งหนังสือเล่มและ E-book ลูกค้าสามารถค้นหารายชื่อหนังสือ อ่านรีวิว และสั่งซื้อเพื่อจัดส่งถึงบ้านหรือดาวน์โหลด E-book ได้ทันที ธุรกิจต้องการพัฒนาเว็บไซต์และแอปมือถือใหม่เพื่อเพิ่มความพึงพอใจของลูกค้าและเพิ่มประสิทธิภาพการทำงานภายใน

ตารางวิเคราะห์ 5 Stakeholders ตามเฉลยใน PDF:

Stakeholder ประเภท (Type) Role & Responsibility (บทบาทหน้าที่ในระบบ)
1. Customer (End User) External ใช้แพลตฟอร์มในการค้นหา ซื้อ ดาวน์โหลด E-book รีวิวหนังสือ และให้ข้อเสนอแนะด้านการใช้งาน (Uses platform to search, purchase, download, and review books).
2. Store Manager Internal ดูแลคลังสินค้า จัดการรายการสินค้า จัดโปรโมชัน ตรวจสอบการส่งออเดอร์ และกำหนดกฎเกณฑ์ทางธุรกิจ (Oversees inventory, manages product listings, promotions, and orders).
3. Software Developer Internal ออกแบบและพัฒนาระบบตามความต้องการที่ระบุ รับผิดชอบการเขียนโค้ดและฟังก์ชันการทำงาน (Designs and implements system according to specified requirements).
4. UX/UI Designer Internal ดูแลให้ระบบใช้งานง่าย สะดวกในการใช้งาน ออกแบบส่วนติดต่อผู้ใช้ (UI) สำหรับเว็บและมือถือ (Ensures system is intuitive and easy to use. Designs web/mobile interfaces).
5. Payment Service Provider External บริการภายนอกที่ดูแลการทำธุรกรรมออนไลน์ รับรองความปลอดภัยและความถูกต้องในการชำระเงิน (Third-party service handling secure and compliant online payment transactions).

Case 5: "EasyClinic" Appointment Booking System (หน้า 9-10 ของ PDF — Homework 2)

[โจทย์ภาษาไทย]:
คลินิกเอกชนชื่อ EasyClinic ประสบปัญหาการจัดการคิวผู้ป่วยหน้าคลินิก เนื่องจากมีผู้ป่วยจำนวนมากโทรเข้ามาจองคิว และบางรายไม่มาในเวลานัด ทำให้เสียโอกาสในการให้บริการ เจ้าของคลินิกจึงต้องการระบบออนไลน์ที่ช่วยให้ผู้ป่วยสามารถจองคิว ตรวจสอบเวลานัดหมาย และรับการแจ้งเตือนได้ผ่านมือถือ...

ตารางวิเคราะห์ Stakeholders ทั้ง 6 กลุ่มของ EasyClinic:

Stakeholder ประเภท บทบาทหน้าที่และความรับผิดชอบในระบบ (Role & Responsibility)
1. Clinic Owner (เจ้าของคลินิก) Internal (Sponsor) เป็นผู้อนุมัติงบประมาณและกำหนดเป้าหมายธุรกิจ ต้องการลดปัญหาผู้ป่วยเบี้ยวนัด (No-show) และดูรายงานสถิติการเข้ารับบริการ
2. Patients (ผู้ป่วย/ผู้รับบริการ) External (End User) ลงทะเบียนด้วยเบอร์โทร/เลขบัตรประชาชน เลือกแพทย์ วันเวลานัดหมาย และรับ SMS/Email แจ้งเตือนก่อนนัด 1 วันและ 1 ชั่วโมง
3. Doctors (แพทย์) Internal (User) เข้าสู่ระบบ Dashboard หลังบ้านเพื่อตรวจสอบตารางนัดหมายของตนเอง และปรับตารางเวลาตรวจรักษาตามความจำเป็น
4. Clinic Staff (เจ้าหน้าที่หน้าเคาน์เตอร์) Internal (User) ดูรายการจองคิวทั้งหมด อัปเดตสถานะผู้ป่วย เช่น "มาถึงแล้ว (Arrived)" หรือ "ไม่มาตามนัด (No-show)" และจัดการคิวเฉพาะหน้า
5. Software Development Team Internal / Vendor ออกแบบ พัฒนาระบบให้รองรับทั้ง Web Browser, Android และ iOS ภายใต้งบและระยะเวลาส่งมอบ 3 เดือน
6. Ministry of Public Health / Regulators External (Regulator) หน่วยงานกำกับดูแลมาตรฐานความปลอดภัยของข้อมูลสุขภาพ (HIPAA / แนวทางกระทรวงสาธารณสุข / PDPA)

ถ้าในห้องสอบอาจารย์เปลี่ยนชื่อระบบเป็นอย่างอื่น (เช่น "ระบบซ่อมรถอู่ช่างเอก" หรือ "ระบบสั่งอาหารหอพัก") ให้ใช้ โครงสร้างเทมเพลตมาตรฐาน นี้ในการเขียนตอบ คุณจะได้คะแนนเต็มทันที:

เทมเพลตเขียน Functional Requirements (FR)

1. The system shall allow [User] to register and log in using [Email/Phone/ID].
2. The system shall display [Product/Service/Menu listings] with clear details.
3. The system shall allow users to [Select/Book/Add to Cart] items.
4. The system shall calculate total costs and display an order/booking summary.
5. The system shall accept online payments via [Mobile banking / Credit card].
6. The system shall send automated [SMS / Email] confirmation and reminder alerts.

เทมเพลตเขียน Non-Functional Requirements (NFR)

• Usability: First-time users shall complete tasks within [5–10 minutes] with an intuitive interface.
• Performance: The system response time shall be under [1–3 seconds] for [300–1,000 concurrent users].
• Reliability: The system shall maintain at least [99.9% uptime] during operational hours.
• Security: User passwords and financial data must be encrypted using SSL/TLS in compliance with PDPA.

เทมเพลตเขียน Domain Requirements

1. The system must strictly comply with national privacy legislation (PDPA / HIPAA).
2. The system shall generate daily business operations and analytical sales reports for management.
3. The system must integrate with [University / Organization Central Authentication Server].

เทมเพลตเขียน Constraints (ข้อจำกัด)

1. Technology: Must be developed using [Flutter / React / Laravel] supporting [Android, iOS, and Web].
2. Budget: Total development cost must not exceed [Budget from scenario] Baht.
3. Timeline: The project must be completed and deployed within [2–3 months].
