1. หลักการอ่านโจทย์ & วิธีตอบข้อสอบ

🔑 กฎทอง: ข้อสอบ SE มี 2 ประเภทเท่านั้น

ประเภท 1 — วิเคราะห์ Case Study
  • ให้ Case Study (สถานการณ์จำลอง) เป็นภาษาอังกฤษ
  • ให้วิเคราะห์: FR, NFR, Domain, Constraint, Stakeholder, Product Vision
ประเภท 2 — อธิบายทฤษฎี
  • ถาม Agile Manifesto / 4 Core Values
  • ถาม Scrum Framework (3 Roles, 5 Events, 3 Artifacts)
  • อาจให้ประยุกต์กับ Case Study ที่กำหนดให้

📖 ขั้นตอนอ่านโจทย์ Case Study (5 ขั้นตอน)

1
อ่านโจทย์ผ่านรอบแรก — จับ "ใคร ทำอะไร ทำไม"
อ่านทั้งโจทย์ให้จบก่อน 1 รอบ จับใจความว่า: ใครเป็นเจ้าของ/ใช้ระบบ (Stakeholders), ระบบนี้ทำอะไร (ชื่อ + ประเภทแอป/เว็บ), ทำไมต้องสร้าง (ปัญหาที่แก้)
2
อ่านรอบ 2 — ขีดเส้นใต้ & จำแนก 6 หมวด
อ่านทีละประโยค ขีดเส้นใต้คำสำคัญ แล้วเขียนตัวย่อกำกับไว้ข้างหน้าแต่ละประโยค:
  • FR = กริยาสั่งงาน (register, log in, search, add to cart, pay, send, notify, generate report)
  • NFR = ตัวเลข/คุณภาพ (within 2 seconds, 1000 concurrent users, 99.9% uptime, SSL, encrypted, senior-friendly)
  • Domain = กฎเฉพาะทาง (PDPA, HIPAA, อีเมล @kmutnb.ac.th, FIFO queue)
  • Constraint = ข้อจำกัดตายตัว (Flutter, Laravel, budget ≤ 200,000, within 3 months)
  • Stakeholder = คนหรือหน่วยงาน (owner, student, staff, doctor, patient, payment provider)
  • Vision = ปัญหาที่แก้ + จุดเด่น (ใช้เขียน Moore's Template)
3
ดูว่าข้อสอบถามอะไร — อ่านคำสั่งท้ายโจทย์ก่อนเขียน
ข้อสอบจะบอกชัดเจนว่าต้องการอะไร เช่น Identify 3 FR, 2 NFR, 1 Constraint อย่าเขียนมากกว่าหรือน้อยกว่าที่ถาม
4
เขียนคำตอบเป็นข้อๆ — ใช้ Template ภาษาอังกฤษ
ใช้โครงสร้างประโยคสำเร็จรูปจากด้านล่างเพื่อเก็บ +5 คะแนนพิเศษ
✅ เขียนเป็นข้อ 1. 2. 3. อย่าเขียนเป็นย่อหน้ายาว — อาจารย์ตรวจง่ายกว่า
5
ตรวจทานก่อนส่ง — เช็คว่าครบตามจำนวนที่ถาม
นับจำนวนข้อ FR / NFR / Stakeholder ว่าตรงกับที่โจทย์ระบุหรือไม่ ตรวจสอบว่าไม่มีข้อใดซ้ำกัน

🔍 เทคนิคจำแนก FR vs NFR vs Domain vs Constraint (สังเกตคำ)

ประเภท 🔑 คำ/สัญญาณที่จะเจอในโจทย์ ตัวอย่างประโยคในโจทย์
FR
Functional		 กริยาสั่งงาน: allow, enable, shall, must, register, log in, search, display, calculate, notify, send, generate, book, pay "Users can register using email"
"The system displays a menu list"
"Send a confirmation email"
NFR
Non-Functional		 ตัวเลข + คุณภาพ: within X seconds, concurrent users, uptime, encrypted, SSL, intuitive, user-friendly, senior-friendly, backup "Respond within 2 seconds"
"Support 1,000 concurrent users"
"Encrypted using AES-256"
Domain กฎเฉพาะทาง: comply with, regulation, PDPA, HIPAA, policy, standard, university email, กฎทางธุรกิจ "Must comply with PDPA"
"Login with @kmutnb.ac.th only"
Constraint ข้อจำกัดตายตัว: developed using, framework, budget, cost, within X months, platform, language "Built with Flutter"
"Budget not exceeding 200,000 Baht"
"Completed within 3 months"

✍️ Template ประโยคภาษาอังกฤษสำเร็จรูป (ลอกไปเขียนได้เลย)

ประเภทโครงสร้างประโยค (เติม [...] ตามโจทย์)
FR The system shall allow [user] to [action].
The system must [calculate / display / send / generate] [object].
[User] shall be able to [action] through [channel].
NFR The system must respond to user actions within [X] seconds.
The system shall support at least [X] concurrent users.
All [data type] must be encrypted using [SSL/TLS / AES-256].
The interface must be [intuitive / senior-friendly / accessible].
The system must maintain at least [X]% uptime per month.
Domain The system must comply with [PDPA / HIPAA / regulation name].
The system must integrate with [existing system / university SSO].
Constraint The application must be developed using [framework / language].
The total project cost must not exceed [budget].
The project must be completed within [X] months.
The application must run on [Android / iOS / Web].
Stakeholder [Stakeholder Name] is responsible for [role description].
As an [internal/external] stakeholder, [Name] [does what].
📋 Cheat Sheet

2. ตารางจำแนก Requirements 4 ประเภท

ประเภท คำอธิบาย (ไทย) & Definition (EN) ตัวอย่างที่พบบ่อยในข้อสอบ
Functional Requirement (FR) EN: What the system should do — specific services, functions, and behaviors.
TH: ระบบต้องทำอะไรได้บ้าง — ฟังก์ชันและบริการเฉพาะ 		• สมัครสมาชิก / ล็อกอิน (Register / Login)
• ค้นหา / แสดงรายการสินค้า (Search / Display catalog)
• เพิ่มลงตะกร้า / คำนวณราคา (Add to cart / Calculate total)
• ชำระเงินออนไลน์ (Online payment)
• ส่งอีเมลยืนยัน / แจ้งเตือน (Email/SMS notification)
• สร้างรายงานยอดขาย (Generate sales report)
Non-Functional Requirement (NFR) EN: How well the system performs — quality attributes and properties.
TH: ระบบทำงานดีแค่ไหน — ประสิทธิภาพ ความปลอดภัย ความง่าย 		• Performance: ≤2 sec response, ≥500 concurrent users
• Usability: ทำรายการเสร็จใน 5 นาที, senior-friendly
• Security: SSL/TLS, AES-256, PDPA compliance
• Reliability: Uptime ≥99.5%, daily backup at 2AM
Domain Requirement EN: Business rules, industry regulations, or organizational policies.
TH: กฎเกณฑ์เฉพาะทางธุรกิจ กฎหมาย หรือนโยบายองค์กร 		• ปฏิบัติตาม PDPA / HIPAA
• ล็อกอินได้เฉพาะอีเมล @kmutnb.ac.th
• ระบบรองรับ 2 ภาษา (Thai & English)
• ระยะยืมหนังสือ 14 วัน (Business rule)
Constraint EN: Hard limits on technology, budget, time, or platform.
TH: ข้อจำกัดตายตัวทางเทคนิค งบประมาณ เวลา แพลตฟอร์ม 		• พัฒนาด้วย Flutter / Laravel PHP
• รองรับ Android & iOS
• งบไม่เกิน 200,000 - 350,000 บาท
• เสร็จภายใน 2-4 เดือน
⚠️ ข้อควรระวัง: FR vs NFR แยกยังไง?
FR = ถ้าขาด feature นี้ระบบไม่ทำงาน (เช่น ถ้าไม่มี Login ใช้ระบบไม่ได้)
NFR = ถ้าขาดระบบยังทำงานได้ แต่คุณภาพแย่ (เช่น ช้ามากแต่ยังโหลดได้)
Domain = ถ้าขาดอาจผิดกฎหมายหรือผิดนโยบายองค์กร
Constraint = ถ้าฝืนทำไม่ได้ เพราะเป็นข้อจำกัดจากภายนอก (เงิน/เวลา/เทคโนโลยี)
🎯 Product Vision

3. แม่แบบ Moore's Vision Template

ข้อสอบมักให้ Case Study แล้วให้เขียน Product Vision ตาม Template นี้:

FOR [กลุ่มผู้ใช้เป้าหมาย / Target Customer]
WHO [ปัญหาหรือความต้องการ / Statement of Need]
THE / OUR PRODUCT [ชื่อผลิตภัณฑ์ + ประเภท / Product Name & Category]
THAT [ประโยชน์หลักที่แก้ปัญหา / Key Benefit]
UNLIKE [ทางเลือกเดิมหรือคู่แข่ง / Competitive Alternative]
OUR PRODUCT [จุดเด่นที่เหนือกว่า / Primary Differentiation]

🔑 วิธีเขียน Product Vision จากโจทย์ Case Study:

  1. FOR — หาคำว่า "for students", "for patients", "for customers" ในโจทย์
  2. WHO — หาประโยคที่บอกปัญหา: "who struggle with...", "who need to...", "long queue", "inefficient"
  3. OUR PRODUCT — ใส่ชื่อระบบ + ประเภท เช่น "PizzaFriend - Mobile Ordering App"
  4. THAT — ดึง FR เด่นๆ 2-3 อัน: "enables online ordering, secure payment, and real-time tracking"
  5. UNLIKE — นึกว่าก่อนมีแอปนี้ ทำยังไง: "manual phone-call", "walk-in queue", "LINE groups"
  6. OUR PRODUCT — สรุปจุดเด่น: "offers a 5-minute seamless experience with cross-platform access"

ตัวอย่าง: iLearn System

FOR teachers and educators
WHO need a way to help students access web-based learning resources and applications
THE iLearn System IS A configurable open learning environment
THAT allows teachers to assign and manage learning resources per course and class
UNLIKE traditional VLEs such as Moodle that focus on document management
OUR PRODUCT focuses on age-appropriate learning by integrating videos, simulations, and web resources
📦 Case Study 1

FreshMart — E-commerce Website (เว็บขายของชำออนไลน์)

📖 แปลโจทย์
FreshMart เป็นร้านขายของชำออนไลน์แห่งใหม่ของคุณสุพรรษา ต้องการส่งมอบผักสด ผลไม้ และของใช้ประจำวันถึงมือลูกค้าในกรุงเทพฯ ต้องการเว็บไซต์ที่ใช้งานง่ายเพื่อสั่งซื้อออนไลน์และจัดส่งอย่างรวดเร็ว

FR Functional Requirements

  1. The system shall allow customers to register and log in using email and password.
    → ลงทะเบียนและเข้าสู่ระบบด้วยอีเมลและรหัสผ่าน
  2. The system shall display products categorized into sections (vegetables, fruits, bakery).
    → แสดงสินค้าแบ่งตามหมวดหมู่อย่างชัดเจน
  3. Customers shall be able to add, edit, and remove items from a shopping cart.
    → เพิ่ม แก้ไข และลบสินค้าในตะกร้าได้
  4. The system shall calculate and display the total price of cart items.
    → คำนวณและแสดงยอดราคารวมในตะกร้า
  5. Customers shall select available delivery time slots for orders.
    → เลือกรอบเวลาจัดส่งได้
  6. The system shall accept payments via credit cards, debit cards, and mobile banking.
    → ชำระเงินผ่านบัตรเครดิต บัตรเดบิต และ Mobile Banking
  7. The system shall send an order confirmation email with delivery details.
    → ส่งอีเมลยืนยันคำสั่งซื้อพร้อมรายละเอียดจัดส่ง

NFR Non-Functional Requirements

  • Usability: First-time users can complete an order in <10 minutes. → ลูกค้าใหม่สั่งซื้อเสร็จใน 10 นาที
  • Performance: Respond within 3 seconds; support ≥500 concurrent users. → ตอบสนอง 3 วินาที รองรับ 500 คนพร้อมกัน
  • Reliability: ≥99.9% uptime; automated daily backup at 2:00 AM. → เสถียร 99.9% สำรองข้อมูลทุกวันตี 2
  • Security: Customer data encrypted using SSL/TLS. → เข้ารหัสข้อมูลด้วย SSL/TLS

Domain Domain Requirements

  • Must comply with Thailand's PDPA. → ปฏิบัติตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล
  • Must support bilingual display (Thai and English). → รองรับ 2 ภาษา

Constraint Constraints

  • Framework: Laravel PHP | Server: Linux-based in Thailand
  • Budget: ≤200,000 Baht | Timeline: 3 months
🎓 Case Study 2

KMUTNB University Cafeteria — Mobile App (แอปสั่งอาหาร มจพ.)

📖 แปลโจทย์
โรงอาหารมหาวิทยาลัยเทคโนโลยีพระจอมเกล้าพระนครเหนือ (มจพ.) ต้องการพัฒนาแอปมือถือสั่งอาหารสำหรับนักศึกษา ล็อกอินด้วยอีเมลมหาวิทยาลัย ดูเมนู เลือกอาหาร ชำระเงินผ่าน Mobile Banking / Digital Wallet ร้านค้าได้รับแจ้งเตือนทันที นักศึกษาเห็นเวลารับอาหาร รองรับ 1,000 คนพร้อมกัน

FR Functional Requirements

  1. Students must log in using their university email (@kmutnb.ac.th).
    → ล็อกอินด้วยอีเมล มจพ.
  2. Students can browse menus, select food items, and add to cart.
    → ดูเมนู เลือกอาหาร ใส่ตะกร้า
  3. The system must calculate total prices and display order summary.
    → คำนวณราคารวมและแสดงสรุปคำสั่งซื้อ
  4. Students can pay via mobile banking or digital wallets.
    → ชำระผ่าน Mobile Banking / Digital Wallet
  5. The system must immediately notify cafeteria staff on new orders.
    → แจ้งเตือนร้านค้าทันทีเมื่อมีออเดอร์ใหม่
  6. Display estimated pickup time for students.
    → แสดงเวลาประมาณการรับอาหาร

NFR Non-Functional Requirements

  • Performance: Support ≥1,000 concurrent users without lag. → รองรับ 1,000 คนพร้อมกันช่วงเที่ยง
  • Usability: User-friendly for quick learning. → ใช้งานง่าย เรียนรู้ได้เร็ว

Domain Domain Requirements

  • Must integrate with university SSO / account system. → เชื่อมต่อระบบบัญชีผู้ใช้มหาวิทยาลัย
  • Comply with university data privacy policies. → ปฏิบัติตามนโยบายความเป็นส่วนตัวของ มจพ.

Constraint Constraints

  • Platform: Android & iOS | Timeline: 2 months
🍕 Case Study 3

PizzaFriend — Mobile App (แอปสั่งพิซซ่าคุณพลอย)

📖 แปลโจทย์
คุณพลอยเจ้าของร้านพิซซ่าย่านมหาวิทยาลัย พบว่านักศึกษาต้องรอคิวนานมากช่วงพักเที่ยง จึงสร้างแอป "PizzaFriend" ให้ลงทะเบียน/ล็อกอิน ดูเมนูพร้อมรูป เลือกขนาด แป้ง ท็อปปิ้ง คำนวณเงิน ชำระผ่านโอนเงิน/บัตรเครดิต ส่งใบเสร็จอีเมล มีรายงานยอดขาย/สินค้าขายดี ลูกค้าใหม่สั่งเสร็จใน 5 นาที โหลดเมนูใน 2 วินาที รองรับ 300 คน ปฏิบัติตาม PDPA พัฒนาด้วย Flutter ให้เสร็จใน 3 เดือน

FR Functional Requirements

  1. Register and log in using email and password. → ลงทะเบียนและล็อกอิน
  2. Display pizza menu with photos, descriptions, and prices. → แสดงเมนูพร้อมรูปและราคา
  3. Select pizza sizes, crusts, toppings, and add to cart. → เลือกขนาด แป้ง ท็อปปิ้ง
  4. Calculate total costs and display order summary. → คำนวณราคารวม
  5. Payment via mobile banking transfers and credit cards. → ชำระเงินผ่านโอนเงินและบัตรเครดิต
  6. Send order confirmation receipt via email. → ส่งใบเสร็จทางอีเมล
  7. Generate daily sales reports and best-selling item analytics. → รายงานยอดขาย/สินค้าขายดี

NFR Non-Functional Requirements

  • Usability: First-time order completed within 5 minutes. → สั่งครั้งแรกเสร็จใน 5 นาที
  • Performance: Menu loads ≤2 sec; support 300 concurrent users. → โหลด 2 วินาที รองรับ 300 คน
  • Security: Encrypt financial data; comply with PDPA. → เข้ารหัสข้อมูลเงิน ปฏิบัติตาม PDPA

Domain Domain | Constraint Constraints

  • Domain Daily sales tracking & promotion analytics for pizza store management
  • Constraint Framework: Flutter | Platform: Android & iOS | Timeline: 3 months

Vision Product Vision (Moore's Template)

FOR university students and busy lunch-time customers
WHO need a fast and convenient way to order customized pizza without waiting in long queues
OUR PRODUCT PizzaFriend — Mobile Pizza Ordering App
THAT allows users to customize pizzas, pay online, and track orders with fast pickup times
UNLIKE traditional walk-in counter ordering and phone-call ordering
OUR PRODUCT offers a seamless 5-minute ordering flow with Flutter-powered cross-platform accessibility

🏥 Case Study 5

EasyClinic — Appointment Booking System (ระบบจองคิวคลินิก)

📖 แปลโจทย์
คลินิกเอกชน EasyClinic ประสบปัญหาคนไข้โทรจองคิวแล้วไม่มาตามนัด (No-show) ทำให้เสียโอกาส จึงต้องการระบบจองคิวออนไลน์ผ่านเว็บและแอป ลงทะเบียนด้วยเบอร์โทร/เลขบัตรประชาชน เลือกแผนก/หมอ/วันเวลา ส่ง SMS/Email แจ้งเตือนล่วงหน้า 1 วันและ 1 ชม. แพทย์มี Dashboard ดูตาราง เจ้าหน้าที่อัปเดตสถานะ "มาแล้ว"/"ไม่มา" มีรายงานสถิติรายวัน เข้ารหัสตาม HIPAA/สธ. รองรับผู้สูงอายุ (Senior-friendly) เสร็จใน 3 เดือน

9.2 Scrum Framework — โครงสร้าง 3-5-3

👥 3 Roles (บทบาท)

RoleResponsibilities (EN + TH)
Product Owner (PO) EN: Maximizes business value of the product. Creates, maintains, and prioritizes the Product Backlog. Decides which features to build first and accepts/rejects completed work.
TH: กำหนดทิศทางผลิตภัณฑ์ สร้างและจัดลำดับ Product Backlog ตัดสินใจว่าทำฟีเจอร์ใดก่อน-หลัง ตรวจรับงาน
Scrum Master (SM) EN: Acts as a servant leader and facilitator. Ensures the team follows Scrum practices. Removes impediments/blockers and protects the team from external distractions.
TH: ผู้นำรับใช้ ดูแลให้ทีมทำงานตามหลัก Scrum กำจัดอุปสรรค ปกป้องทีมจากสิ่งรบกวน
Developers
(Dev Team)		 EN: A cross-functional, self-organizing team (3–9 people: developers, testers, designers). Turns selected Backlog items into a working Increment each Sprint.
TH: ทีมข้ามสายงาน บริหารตัวเอง แปลง Backlog เป็นโค้ดที่ทำงานได้จริง

⏱️ 5 Events (กิจกรรม)

EventPurpose (EN + TH)
1. Sprint EN: A fixed time-boxed period (1–4 weeks) during which the team creates a usable, potentially shippable Increment.
TH: กรอบเวลาคงที่ 1–4 สัปดาห์ เพื่อสร้างชิ้นงานที่พร้อมใช้
2. Sprint Planning EN: Meeting at the start of the Sprint. PO presents backlog items, team selects items and defines the Sprint Goal and Sprint Backlog.
TH: ประชุมต้น Sprint วาง Sprint Goal เลือก Backlog items
3. Daily Scrum
(Stand-up)		 EN: A 15-minute daily synchronization meeting. Each member answers 3 questions:
• What did I do yesterday?
• What will I do today?
• Are there any impediments?
TH: ประชุมสั้น 15 นาทีทุกวัน ตอบ 3 คำถาม เมื่อวานทำอะไร / วันนี้ทำอะไร / มีอุปสรรคไหม
4. Sprint Review EN: End-of-Sprint meeting to demonstrate (demo) the working Increment to stakeholders and gather feedback. Product Backlog may be adapted based on feedback.
TH: สาธิตชิ้นงานจริงให้ Stakeholders ดู รับ Feedback
5. Sprint Retrospective EN: An internal team meeting after Sprint to reflect on processes, tools, and collaboration. Identify improvements for the next Sprint.
TH: ทบทวนกระบวนการภายในทีม หาข้อดี ข้อเสีย วางแผนปรับปรุงรอบถัดไป
💡 ข้อสอบมักถาม: Daily Scrum vs Sprint Retrospective ต่างกันอย่างไร?
Daily Scrum = ประชุมสั้น 15 นาทีทุกวัน เน้นติดตามงานว่าแต่ละคนทำอะไรอยู่ มีอุปสรรคอะไร
Sprint Retrospective = ประชุมครั้งเดียวตอนจบ Sprint เน้นทบทวนกระบวนการทำงานของทีม (ไม่ใช่ตัวงาน) เพื่อปรับปรุงการทำงานรอบถัดไป

📦 3 Artifacts (ผลผลิต)

ArtifactDescription (EN + TH)
Product Backlog EN: An ordered, evolving list of all known requirements, features, and fixes for the product. Owned and prioritized by the Product Owner.
TH: รายการ Requirements และฟีเจอร์ทั้งหมดที่จัดลำดับความสำคัญ ดูแลโดย PO
Sprint Backlog EN: The set of Product Backlog items selected for the current Sprint plus a plan for delivering them.
TH: Backlog items ที่เลือกมาทำใน Sprint ปัจจุบัน พร้อมแผนการพัฒนา

TH: ชิ้นงานซอฟต์แวร์ที่เสร็จสมบูรณ์ ทำงานได้จริง ผ่านเกณฑ์ DoD

📝 ข้อ 5: Scrum Events & Agile Values (6 คะแนน)

โจทย์: Explain Daily Scrum vs Sprint Retrospective. Why does Agile value "Responding to Change" over "Following a Plan"?

แนวตอบ (English):

1. Daily Scrum vs Sprint Retrospective:

  • Daily Scrum: A 15-minute daily synchronization meeting where developers inspect progress toward the Sprint Goal, plan the next day's work, and identify impediments.
  • Sprint Retrospective: An end-of-Sprint meeting where the Scrum Team reflects on team processes, tools, and collaboration to identify actionable improvements for the next Sprint.

2. Responding to Change over Following a Plan:

  • In modern software engineering, business environments, user demands, and technology change rapidly.
  • Blindly adhering to an outdated plan leads to delivering products that no longer meet customer needs.
  • By embracing change, Agile teams continuously adapt based on stakeholder feedback and deliver maximum customer value at every iteration.
