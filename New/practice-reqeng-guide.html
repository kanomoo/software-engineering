⚡ 1. โมเดลการทำข้อสอบ 3 ขั้นตอน (The 3-Step Solving Engine)

ขั้นที่ 1: สแกนโจทย์หา Key Verbs & Numbers

อ่านโจทย์ภาษาอังกฤษแบบ Skimming อย่าเพิ่งแปลทุกคำ ให้ใช้ดินสอวงกลม "คำกริยาการทำงาน" (Action Verbs) และ "ตัวเลขชี้วัด" (Time, Users, %, Budget, Deadline)

ขั้นที่ 2: โยนข้อความลง 4 ถังความคิด

จำแนกข้อมูลในโจทย์ออกเป็น 4 หมวดทันที:
• FR: ระบบทำอะไร
• NFR: คุณภาพ/ตัวเลขวัดผล
• Domain: กฎหมาย/ระบบเฉพาะองค์กร
• Constraints: ภาษา/งบ/เวลา

ขั้นที่ 3: สวมสูตรโครงสร้างประโยคมาตรฐาน

นำข้อความที่สกัดได้มาเขียนเป็นประโยคที่สมบูรณ์ตามไวยากรณ์ "ระบบต้อง..." หรือ "The system shall..." โดยใส่ตัวเลขชี้วัด (Metrics) กำกับเสมอ

🔍 2. ตารางเทียบ Keyword 4 ถังความคิด (Keyword Hunting Matrix)

เมื่อเจอกลุ่มคำเหล่านี้ในโจทย์ภาษาอังกฤษ ให้รู้ทันทีว่าจะต้องนำไปตอบในหมวดหมู่ใด:

หมวดหมู่ คีย์เวิร์ดภาษาอังกฤษที่พบบ่อยในโจทย์ ความหมายและการตีความ ตัวอย่างการแปลงไปตอบ
Functional (FR)
(ระบบทำอะไร)		 register, login, scan barcode/RFID, calculate price/fine, send notification/SMS/email, verify OTP/QR, generate daily report, pay via Mobile Banking เป็น หน้าที่หรือบริการ ที่ระบบส่งมอบให้ผู้ใช้งาน สามารถกดปุ่มหรือสั่งการให้เกิดขึ้นได้ "ระบบต้องส่ง SMS แจ้งรหัส OTP 6 หลักให้ผู้รับเมื่อพัสดุเข้าตู้"
Non-Functional
(ทำงานได้ดีแค่ไหน)		 within X seconds, X concurrent users, intuitive / user-friendly, without training / within X minutes, encrypted, 99.9% availability, downtime < X s เป็น เกณฑ์คุณภาพ/ข้อจำกัดด้านประสิทธิภาพ ต้องระบุตัวเลขที่วัดผลได้ (Testable metric) เสมอ "ระบบต้องตอบสนองภายใน 2 วินาที และรองรับพร้อมกัน 500 คน"
Domain Reqs
(บริบทเฉพาะวงการ)		 PDPA / GDPR, HIPAA / Ministry of Public Health, Active Directory, Dewey Decimal / LCC, PromptPay standard, ISO standard เป็น กฎหมาย, ระเบียบวิชาชีพ, หรือระบบเฉพาะของหน่วยงานนั้น ที่บังคับให้ซอฟต์แวร์ต้องรองรับ "ระบบต้องปฏิบัติตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)"
Constraints
(ข้อจำกัดทีมพัฒนา)		 built using Flutter/React/Java, run on Linux/Windows IoT, budget not exceeding X Baht, completed within X months เป็น ข้อผูกมัดหรือกรอบจำกัด ด้านเครื่องมือ งบประมาณ หรือเวลาที่ลูกค้ากำหนดให้ผู้พัฒนาปฏิบัติตาม "ต้องพัฒนาด้วย Flutter รองรับ iOS/Android งบไม่เกิน 250,000 บาท เสร็จใน 3 เดือน"

✍️ 3. สูตรสำเร็จรูปในการเขียนประโยคคำตอบ (Answering Syntax Formulas)

1. สูตรเขียน Functional Requirements (FR)

สูตรภาษาไทย: ระบบต้อง + [อนุญาตให้ใคร / ดำเนินการอะไร] + [กริยาการทำงาน] + [ข้อมูลหรือผลลัพธ์] + [เงื่อนไขเพิ่มเติม (ถ้ามี)]
Formula (EN): The system shall [allow Actor to / automatically] + [Action Verb] + [Data/Object] + [when Condition].
  • ✔️ ตัวอย่าง 1: ระบบต้องอนุญาตให้นักศึกษาลงทะเบียนและเข้าสู่ระบบด้วยอีเมลของมหาวิทยาลัยได้
  • ✔️ ตัวอย่าง 2: ระบบต้องคำนวณค่าธรรมเนียมการฝากเกินเวลาโดยอัตโนมัติหากฝากพัสดุไว้นานเกิน 48 ชั่วโมง

2. สูตรเขียน Non-Functional Requirements (NFR 4 ด้านหลัก)

*ข้อสอบจะหักคะแนนทันทีหากเขียน NFR ลอยๆ โดยไม่มีตัวเลขวัดผล (Metrics)*

มิติ NFR สูตรโครงสร้างประโยค (Syntax Formula) ตัวอย่างคำตอบที่ได้คะแนนเต็ม
1. Usability
(ความง่ายในการใช้)		 ระบบต้องออกแบบให้ [กลุ่มผู้ใช้] สามารถ [ทำภารกิจสำเร็จ] ได้ภายในเวลา [X นาที] โดยมีอัตราความผิดพลาดน้อยกว่า [Y%] "หน้าจอต้องใช้งานง่าย ผู้ใช้ใหม่สามารถทำรายการยืมหนังสือเสร็จได้ภายใน 30 วินาที โดยไม่ต้องผ่านการฝึกอบรม"
2. Performance
(ประสิทธิภาพความเร็ว)		 ระบบต้อง [ตอบสนอง / ประมวลผลผลลัพธ์] ภายในเวลาไม่เกิน [X วินาที] "ระบบต้องแสดงผลการค้นหาข้อมูลภายในเวลาไม่เกิน 1.5 วินาที"
3. Capacity / Scalability
(การรองรับผู้ใช้)		 ระบบต้องรองรับผู้ใช้งานพร้อมกันอย่างน้อย [X คน] ในช่วงเวลาเร่งด่วน โดยระบบไม่ล่าช้าหรือหยุดทำงาน "ระบบต้องรองรับผู้ใช้งานพร้อมกันอย่างน้อย 500 คน ในช่วงเวลาเร่งด่วน (12:00-13:30)"
4. Security
(ความปลอดภัย)		 ข้อมูล [รหัสผ่าน / ข้อมูลการเงิน / ข้อมูลสุขภาพ] ต้องได้รับการ [เข้ารหัส / จำกัดสิทธิ์] ตามมาตรฐานความปลอดภัย "ข้อมูลการชำระเงินและรหัส OTP ต้องได้รับการเข้ารหัส (Encryption) ตลอดการส่งผ่านเครือข่าย"

👥 4. สูตรผ่า 2 ซีก: การวิเคราะห์ Stakeholders & Roles

เมื่อโจทย์ให้ระบุผู้มีส่วนได้ส่วนเสีย 5–7 คน ให้ใช้เทคนิค "ผ่าครึ่ง Internal vs External" เพื่อให้ได้คะแนนครบทุกมิติ:

🏢 ฝั่งที่ 1: Internal Stakeholders (คนในโครงการ)

  • Project Owner / Sponsor: กำหนดเป้าหมาย งบประมาณ และตรวจ Daily Report
  • Staff / Operator: พนักงานหน้างาน เช่น แคชเชียร์, คนขับรถ, พยาบาล, บรรณารักษ์
  • Manager / Supervisor: ผู้จัดการแผนก ดูแลภาพรวมและสถิติ
  • Development & UX Team: โปรแกรมเมอร์และผู้ออกแบบหน้าจอ
  • System Administrator: แอดมินดูแล Server และความปลอดภัย

🌍 ฝั่งที่ 2: External Stakeholders (คนนอกโครงการ)

  • End Users / Customers: ผู้ใช้งานปลายทาง เช่น นักศึกษา, คนไข้, ลูกค้า
  • Third-party API Providers: ผู้ให้บริการ SMS Gateway, Payment Gateway, GPS
  • Regulatory Authorities: หน่วยงานกำกับกฎหมาย เช่น PDPA, อย., กระทรวงสาธารณสุข
💡 เคล็ดลับการเขียน Role (บทบาทหน้าที่): ห้ามเขียนแค่ชื่อตำแหน่ง เช่น "ลูกค้า: เป็นคนซื้อของ" ❌ (ได้คะแนนน้อย)
➔ ต้องเขียนระบุ Action ชัดเจน: "ลูกค้า (End User): ลงทะเบียนด้วยเบอร์โทร เลือกเมนู สั่งซื้อ ชำระเงินผ่าน Mobile Banking และรับใบเสร็จทาง Email" ✔️ (ได้คะแนนเต็ม)

🔬 5. สาธิตการชำแหละโจทย์จริงทีละประโยค (Exam Dissection Walkthrough)

[ข้อสอบตัวอย่างจริง]: FreshMart Autonomous Store System
FreshMart company is launching a 24/7 cashierless grocery store. Customers scan their membership QR code to enter the gate. Overhead AI vision cameras and weight-sensor shelves track items picked up by shoppers. When walking out through the exit gate, the system automatically charges their credit card and sends an electronic receipt. The automated checkout must take less than 3 seconds per customer. The system must support at least 150 shoppers inside the store simultaneously. Customer camera streams and payment data must comply with Thailand's PDPA privacy laws. The software backend must be built using Python and deployed on Ubuntu Linux with a budget under 500,000 Baht within 4 months.

ผลลัพธ์การชำแหละข้อความออกมาเป็น 4 ถังคำตอบ:

หมวด ข้อความที่ตัดมาจากโจทย์ คำตอบสมบูรณ์แบบที่นำไปเขียนในกระดาษสอบ
FR "Customers scan QR to enter... cameras track items... auto charge card and send e-receipt" 1. ระบบต้องตรวจสอบ QR Code สมาชิกเพื่อปลดล็อกประตูทางเข้า
2. ระบบต้องตรวจจับรายการสินค้าที่ลูกค้าหยิบจากชั้นวางโดยอัตโนมัติผ่านกล้อง AI และเซนเซอร์น้ำหนัก
3. ระบบต้องตัดเงินผ่านบัตรเครดิตและส่งใบเสร็จอิเล็กทรอนิกส์ไปยังมือถือลูกค้าเมื่อเดินผ่านประตูทางออก
NFR "checkout less than 3 seconds... support 150 shoppers simultaneously" • Performance & Usability: ระบบต้องประมวลผลการเช็กเอาต์และคิดเงินเสร็จสิ้นภายในเวลาไม่เกิน 3 วินาที ต่อคน
• Capacity: ระบบต้องรองรับลูกค้าที่เดินเลือกสินค้าในร้านพร้อมกันอย่างน้อย 150 คน โดยไม่เกิดความผิดพลาด
Domain "comply with Thailand's PDPA privacy laws" • ระบบต้องจัดเก็บและประมวลผลภาพถ่ายวิดีโอจากกล้อง AI และข้อมูลการเงินให้สอดคล้องกับ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)
Constraints "Python, Ubuntu Linux, budget under 500,000 Baht, within 4 months" • ระบบ Backend ต้องพัฒนาด้วยภาษา Python บนระบบปฏิบัติการ Ubuntu Linux
• งบประมาณโครงการทั้งหมดต้องไม่เกิน 500,000 บาท
• ระบบต้องพัฒนาและพร้อมเปิดให้บริการจริงภายในระยะเวลาไม่เกิน 4 เดือน

⚠️ 6. ข้อผิดพลาดที่พบบ่อยและจุดที่มักโดนหักคะแนน (Common Pitfalls)

ข้อผิดพลาดที่เด็กมักทำ (Mistake) ตัวอย่างที่ผิด (Wrong ❌) ตัวอย่างที่ถูกต้อง (Correct ✔️)
1. เขียน NFR แบบไม่มีตัวเลข (Goal ลอยๆ) "ระบบต้องรวดเร็วและใช้งานง่าย" ❌ "ระบบต้องตอบสนองใน 2 วินาที และผู้ใช้ใหม่ทำรายการเสร็จใน 3 นาที" ✔️
2. สับสนระหว่าง Constraints กับ FR นำ "ระบบต้องเขียนด้วย Flutter" ไปตอบในช่อง Functional Requirements ❌ แยก "เขียนด้วย Flutter" ไปไว้ในช่อง Constraints เสมอ ✔️
3. เขียน Domain Requirement เป็นฟังก์ชันธรรมดา นำ "ระบบต้องมีปุ่มล็อกอิน" ไปตอบในช่อง Domain ❌ ระบุบริบทเฉพาะ เช่น "ระบบต้องเชื่อมต่อฐานข้อมูล Active Directory ของมหาวิทยาลัย หรือมาตรฐาน PDPA" ✔️
4. เขียนบทบาท Stakeholder กว้างเกินไป "แพทย์: เป็นคนตรวจคนไข้" ❌ "แพทย์ (Internal): เข้าดูคิวนัดผ่าน Dashboard ตรวจรักษาผ่านวิดีโอ และสั่งจ่าย E-Prescription" ✔️
