นอกจากนั้นแล้ว คำนี้ Traceability ภาษาไทยแปลว่าอะไรดี Traceability Trace แปลว่าการ ติดตาม Ability สามารถ Able แปลว่าสามารถ Ability ก็คือสามารถ นะฮะ ดังนั้น มันสามารถที่จะ ติดตาม ได้ ดังนั้น ไอ้ตัว Use Case Diagram เนี่ย จะเชื่อมโยง Requirement ID ก็คือรหัสของความต้องการ เช่น สมมุติมีความต้องการที่ 1 เราก็ต้องใส่รหัสเข้าไปว่า 001, 002 มี User Story มี Design Component มี Code และก็ Test Case นะครับ

คราวนี้ Use Case Diagram ใน Software Development Life Cycle เนี่ย มีขั้นตอนอย่างไรบ้าง นะครับ เค้าบอกว่า Use Case Diagram เนี่ย จะถูกสร้างในช่วง Requirement Analysis เมื่อเราไปเก็บข้อมูลมาจาก User เช่น ไปสัมภาษณ์มา User อยากให้เราทำเว็บไซต์นั้น เว็บไซต์นี้ เราอยากจะดูข้อมูลรายละเอียดมากขึ้น ก็เลยต้องไปสัมภาษณ์ พอหลังจากการสัมภาษณ์เนี่ย จะเป็นการดึงข้อมูลความต้องการออกมา ซึ่งมันออกมาเป็นข้อความ มาเป็นเนื้อหา มาเป็นการอัดเสียง หรืออะไรพวกนี้ นะครับ ดังนั้น เราจึงต้องเอามาทำการ Requirement Analysis วิเคราะห์ นะครับ เพื่อใช้ในการอ้างอิงในการพัฒนาระบบทั้งวงจร ฉะนั้น Use Case Diagram จึงเป็นตัวใช้ในการอ้างอิงในช่วงที่เราพัฒนาระบบ เช่นเดียวกัน

ดังนั้น ตาม Flow เนี่ยเค้าบอกว่า เค้าบอกว่า เริ่มต้นจากการที่ธุรกิจ ธุรกิจหนึ่งเนี่ย มีความต้องการ ให้พัฒนาอะไรสักอย่างหนึ่งขึ้นมา เป็นธุรกิจกำหนดปัญหา แล้วมอบหมาย จากนั้น ทีมก็จะต้องไป เอ่อ จัดการกับความต้องการ ไป get requirement ไปสัมภาษณ์ ไป interview มา แล้วก็เขียนออกมาเป็น Use Case Diagram เมื่อเขียนเสร็จแล้ว ก็ทำเป็น spec ออกมา แล้วก็ไปออกแบบระบบ นะครับ

ควรตั้งชื่อตามบทบาท อันนี้แนะนำ นะครับ ว่าการตั้งชื่อ Actor จะให้ตั้งชื่อตามบทบาท ไม่ควรใช้ชื่อเฉพาะ ยกตัวอย่างเช่น ระบบ REG ไม่ควรใช้ชื่ออาจารย์สมชาย ไม่ได้ นะครับ หรือใช้ว่า User 1 ก็ไม่ได้ มันไม่รู้ว่าเป็นใคร Person ก็ไม่ได้ Computer ก็ไม่ได้ ควรจะเฉพาะเจาะจงไปนิดนึงว่าเป็นบทบาทอะไร เช่น Teacher, Professor, Staff ประมาณนี้ พอได้ นะครับ แต่ไม่ใช่ชื่อเฉพาะของบุคคลนั้นๆ

ข้อผิดพลาด ที่จะเกิดขึ้น นะครับ ข้อผิดพลาด ในการระบุ Actor ที่ ไม่ควรเป็น อย่างเช่น เราไม่ควรจะให้ Database เป็น Actor, Web Server ไม่ควรเป็น Actor, Mobile Application ไม่ควรเป็น Actor สิ่งเหล่านี้ มันอยู่ภายในระบบ ถ้าคุณต้องการเค้าเป็น Actor อย่างเช่น Gateway อย่างเช่น ระบบตู้ ATM เนี่ย ไอ้ตู้ไปติดต่อกับ เอ่อ 3BB หรือว่าแบงก์ Gateway เพื่อติดต่อ แล้วค่อยไปทางออก ตัวข้อมูล เนาะ ประมาณอย่างงี้ นะ สิ่งที่ควรจะเป็น ตามที่เห็นเนี่ย นะครับ แล้วก็เป็น Payment Gateway, Delivery Service อะไรอย่างงี้ นะครับ

ระบุ Use Case เราจะระบุ เอ่อ เค้าเรียกว่า ไม่ใช่ Good Identify Use Case เนี่ย เราจะเริ่มจากตรง Actor ก่อน สมมุติว่า เราต้องการไปกำหนด Use Case ขึ้นมา นะครับ ให้เราดูว่า เอ่อ เป้าหมาย ของ Actor เค้าทำอะไร นะครับ ก็ให้ดูของ เอ่อ ถามว่า เช่นถามว่า Actor เนี่ย ต้อง ต้องการระบุเป้าหมายอะไร เมื่อใช้ระบบ อย่างเช่น ตู้ ATM อย่างเงี้ย นะฮะ เอ่อ คนที่เป็น Actor Customer ของแบงก์เนี่ย เค้าต้องการอะไรจากตู้ ATM ต้องการฝาก เราก็เขียน Deposit ต้องการถอนเงิน ก็ Withdrawal ต้องการโอน ก็ Transfer โอเค นะครับ และวิธีการตั้งชื่อของชื่อ Use Case เนี่ย ก็จะเป็นคำกริยา บวกด้วย Object ตัวอย่างเช่น กริยา Create คือสร้าง Account นะ คือ Object Place Order ก็คือ วางคำสั่งซื้อ นะครับ สร้างรีพอร์ต คือ Generate Report อะไรอย่างงี้ นะครับ พยายามหลีกเลี่ยงชื่อที่เป็นคำนาม แล้วจะงง เช่น Order, Product, Report แล้วไง เราจะไม่รู้ว่า เอ่อ ฟังก์ชันใน System เนี่ย ทำอะไร นะครับ

ส่วน ความละเอียดที่เหมาะสม หมายความว่า การที่เราจะเขียนใน Use Case ว่าเป็น Click button, Input name หรือ Validate Email ตัวเนี้ย มันละเอียดเกินไป สิ่งเหล่านี้ จะไปปรากฏใน Diagram อื่น ที่เรียกว่า Activity Diagram นะครับ ดังนั้น เอ่อ ใน Use Case Diagram เราจะมองแค่วว่า ระบบเนี้ย มี ฟังก์ชัน อะไร แต่ไม่อธิบายว่า User ต้องไปกดอะไร หรือ มีตัวเช็ค User ต้องคีย์อะไรเข้าไป ไม่บอก บอกแค่ว่า มี ฟังก์ชันอะไร มองแค่ จากคนข้างนอก มองเห็นฟังก์ชันนั้นเอง นะครับ ว่าตู้ ATM ฝาก ถอน โอน เงิน ประมาณอย่างงี้ นะฮะ

อันนี้ ก็จะเป็นตัวอธิบายนะ เดี๋ยวขอจะไป ตัวอย่าง เลย เรื่องนี้ก็ ไปดูได้ เดี๋ยวผมจะไป สไลด์ ตัว ถัดไป ละนะ เป็น Case Study ตัวอย่าง เอาไป สไลด์ ตัว เอาแบบง่ายก่อน แบบนี้ เป็นสไลด์ ใน Classroom โพสต์ไปให้ เรียบร้อยแล้ว นะครับ ตัวนี้จะเป็น เอ่อ Case Study ระบบ ยืม คืน หนังสือห้องสมุด เอาแบบง่าย นะครับ เอ่อ เป็นตัวอย่างง่าย นะครับ ในการวิเคราะห์ Actor, Use Case แล้วก็ Relationship Relationship ก็คือ เส้นเชื่อม ระหว่าง Use Case กับ Use เอ้ย Use Case กับ Actor หรือ Use Case กับ Use Case เรามาดูโจทย์ ของระบบก่อนนะ โจทย์ เค้า เค้าบอกว่า มหาวิทยาลัย เนี่ย ต้องการพัฒนาระบบ ยืม คืน หนังสือห้องสมุด นักศึกษาสามารถค้นหาหนังสือ และ ยืม หนังสือได้ เจ้าหน้าที่ห้องสมุดสามารถบันทึก การคืน หนังสือได้ เจ้าหน้าที่สามารถ เพิ่ม แก้ไข และลบข้อมูลหนังสือได้ ตรงนี้จะเป็น สิ่งที่ ระบบเค้าต้องการ นะครับ จากนั้น ก็มีเงื่อนไขสำคัญ เค้าบอกว่า ก่อนยืมหนังสือ ระบบต้องตรวจสอบสิทธิการยืมของนักศึกษา ระบบต้องตรวจสอบว่า หนังสือ ยัง ว่าง อยู่ หรือไม่ นะครับ
สิ่งที่เราต้องทำ ก็คือ เราต้องหา ว่า ใครเป็น Actor ของระบบ ในที่ 1

จากนั้น เรามาดูว่า ความสัมพันธ์ ระหว่าง Actor กับ Use Case หรือใน Use Case เอง เนี่ย มัน จะมีความสัมพันธ์ เป็นแบบ หลากหลาย อย่างไรบ้าง นะครับ

เรามาดู ตัว อันแรกก่อน นะครับ อย่าง Case นี้ เนี่ย เค้าวิเคราะห์ว่า Actor มันก็น่าจะมี นักศึกษา นะครับ กับ Librarian เอ่อ Librarian คือ บรรณารักษ์ นะครับ จริงๆ แล้ว คุณจะแอดเป็น เจ้าหน้าที่ ก็ได้ นะ แต่ใน ใน Case Study นี้ ตามที่ตามโจทย์ เนี่ย เค้าบอกว่า มีใครบ้างที่ยืมได้ มีแค่ นักศึกษา เท่านั้น ที่สามารถ ค้นหา ยืม คืน เจ้าหน้าที่ทำอะไร บันทึกการคืน เจ้าหน้าที่สามารถ เพิ่ม และ แก้ไข ไม่ได้พูดถึงเรื่องของอาจารย์ ดังนั้น Requirement บอกอะไร เขียนตามนั้น นะครับ
